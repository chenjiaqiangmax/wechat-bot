把本地大模型（DeepSeek / 任意 OpenAI 兼容接口）接进微信：一个开箱即用的
**微信群聊 AI 机器人**，加上一套微信 4.x Windows 客户端自动化库
（基于 [wechatauto-replica](https://github.com/fanyuantaier/wechatauto-replica) 二次开发，Apache-2.0）。

## 🐳 大肥鱼：微信群 AI 机器人 （采用Agent架构）

`dafeiyu_bot.py` 监听所有会话，别人在群里 @ 它就把问题发给你自建的 LLM，
回答直接发回群里。

### 功能

- **@ 触发 + 免 @ 跟进**：@ 一次后 5 分钟内连续对话不用再 @，冷场自动退出；别人 @ 其他人的消息不抢答
- **群聊长期记忆**：每个群的对话无限累积，估算上下文到 100K token 自动把最老的历史压成摘要（最近几轮原文保留）（可以改）
- **群消息搜索工具**：LLM 可自主调用，搜索**本群**最近 3 天的消息——按关键词、按成员（昵称/备注/wxid），为空返回全部，上限 2000 条；严格限定当前群，杜绝跨群内容串台
- **多节点粘性故障转移**：多个 LLM 节点粘住一台用（保 prefix cache 命中），报错/乱码才切换，切完继续粘
- **纯文本友好**：回复自动禁 Markdown（`**加粗**`、`- 列表`、代码围栏在微信里就是乱码）
- **安全防护**：任何键盘操作前必须确认前台是微信；正文逐字键入（搜索框、文件/图片附件仍用剪贴板），打字读回不一致清空重打一次、仍不一致就不发，不用拼音盲打；发送失败只听不回，等人工重启
- **关键词广告**：群里有人聊到配置的关键词（如「便宜的模型」「便宜的 token」）就自动回一条可配置的广告；支持软/硬两种模式、真 @ 触发者、逐群随机冷却与命中日志，详见下文
- **日志落盘**：`dafeiyu_bot.log`，每行带时间戳，5MB 自动轮转

### 安装

```bash
git clone https://github.com/dazhi666666/wechat-deepseek.git
cd wechat-deepseek
pip install -e .

```

要求：Windows 10/11、**64 位** Python 3.9+、微信 4.x（4.1.12+）已登录。

### 配置与运行

LLM 通过环境变量配置（任意 OpenAI 兼容接口，请求 `{base_url}/chat/completions`）：

| 环境变量 | 说明 | 示例 |
|---|---|---|
| `WECHAT_DEEPSEEK_BASE_URL` | 接口地址（含 `/v1`），逗号分隔可做故障转移 | `https://api.deepseek.com/v1` |
| `WECHAT_DEEPSEEK_API_KEY` | Bearer 令牌；本地部署可留空 | `sk-...` |
| `WECHAT_DEEPSEEK_MODEL` | 模型名 | `deepseek-chat` |
| `WECHAT_DEEPSEEK_DISPLAY` | 微信窗口放在哪块屏（显示器名称子串），`-` 不干预 | `IddSampleDriver` |

管理后台「配置」页等价地写 `bot_config.json`（`API_BASE_URL` / `API_KEY` / `MODEL` / `LLM_TIMEOUT`），
优先级高于环境变量；这几项保存后下一次请求即生效，不用重启。旧版 `API_HOSTS` + `API_PORT`
字段（环境变量 `WECHAT_DEEPSEEK_API_HOSTS` / `_PORT`）读到会自动迁移成 base_url，不再写回。

```bash
python dafeiyu_bot.py                    # 启动机器人，群里 @大肥鱼 触发
python dafeiyu_bot.py --test "在吗"      # 只测 LLM 链路，不连微信
python dafeiyu_bot.py --search "关键词"  # 命令行搜近 3 天群消息（可配 --member/--group）
```

#### 一键启动

**双击项目根目录的 `一键启动.bat`**：检查 Python 与微信是否已登录，8765 空闲时
用 `pythonw` **无窗口**起管理后台（日志写 `admin.log`，不弹第二个窗口），然后在本窗口
跑机器人——日志直接可见，Ctrl+C 或关窗即停止。

**再次双击 = 重启**：启动前先停掉正在跑的机器人（`tools/stop_running.py`）再起
新的，所以不会再出现「已有机器人在运行（PID xxx）」然后退出。停的顺序是先请管理
后台自己停（`/api/bot/stop`）——后台有个监督线程会在机器人退出 3 秒后把它重新
拉起，直杀会和新实例撞车；后台没在监听时才直接结束进程。

机器人被看门狗判定卡死时会以退出码 **75** 退出，脚本认这个码并 3 秒后自动重启；
**退出码 0 表示「已有一个实例在跑，本次没有启动」**——机器人本身仍在正常工作，
不是失败（提示里给出 PID 和日志位置，按任意键关掉这个窗口即可）。
其它退出码（Ctrl+C、真错误）停在 `pause`。

Ctrl+C 之后会主动删掉 `.bot.pid`，并在 3 秒内强制退出——不会把进程留在后台，
下一次双击直接能起来；如果上一次是被强杀的、锁指向一个已经不在的 PID，启动时会
打一行「清掉残留锁」再继续，不会挡住你。

机器人带单实例锁（`.bot.pid`）：重复双击、或脚本与终端各起一个，第二个会直接
提示「已有机器人在运行」并退出。两个实例会抢同一个微信窗口、把会话互相切走，
回复也可能重复发，所以这条锁是必要的（2026-11-14 实测撞出过第二个实例）。
锁文件随进程退出自动删除，`.bot.pid` 已加进 `.gitignore`。

人设、触发词、记忆阈值等都在 `dafeiyu_bot.py` 顶部「配置区」里改，也可以用管理后台改。

### 管理后台

```bash
python -m admin                          # 打开 http://127.0.0.1:8765
```

纯标准库实现、单页前端无外链，内网可用。功能：机器人启停/重启与运行状态、今日提问数/耗时/
工具调用统计、对话记录（含每轮工具调用过程）、实时日志（机器人日志 / 群发日志 / 关键词广告三个页签）、
表情包上传/重命名/删除、配置与人设编辑、
LLM 节点探测和链路测试。

**多群 Agent**：「Agent」页可以给不同的群配不同的鱼——各自的触发名（群昵称）、人设、模型/温度/长度和可用工具，
记忆按 (Agent, 群) 隔离；一个 Agent 可以标成「兜底」接管所有没被认领的群，没被任何 Agent 认领的群不会回答。
存在 `bot_config.json` 的 `AGENTS` 里，机器人检测到文件变化自动热加载，不用重启。

**用量**：机器人把每次 LLM 调用的 token 写进 `usage.jsonl`，「用量」页按天/小时、Agent、群、节点统计输入/输出
和前缀缓存命中率。服务端返回 `cached_tokens`（vLLM 加 `--enable-prompt-tokens-details`）时用真实值，
否则按同节点近期请求的公共前缀估算（页面标「估算」）。配置保存到 `bot_config.json`（已 gitignore），机器人启动时覆盖
`dafeiyu_bot.py` 里的同名常量，优先级高于环境变量。只监听本机 127.0.0.1。

**群发任务**：「群发任务」页可以定时把文本/图片发到多个群或联系人——从机器人见过的会话里勾选（群和联系人都能选），
输入关键词还会查微信通讯录；内容支持纯文本、纯图片（`stickers/` 里的表情），或两者一起。

- **周期**：一次性（到点执行一次后自动停用），或循环——每隔 N 小时 / N 天（含每 2 天、每 7 天）
- **状态**：启用/停用、下次执行时间、最近一次成功/失败原因都在列表里；可以「立即执行」一次或删除
- **存储**：`broadcast_tasks.json`（和 `bot_config.json` 同目录），重启后任务和执行记录都还在，循环任务按原计划继续
- **谁执行**：机器人进程。后台只读写这个文件——只有它持有微信窗口，后台自己去发会和自动回复抢焦点

两个要知道的限制：微信没有「文字+图片合成一条」的消息类型，同时填文本和图片时实际发**两条**；
任务落后太多轮（比如关机三天）只补最近的一轮，不会连环补发。

单个目标打不开（搜不到、点开的是别的会话）原本会耗尽底层重试、拖一两分钟；现在有
**25 秒上限**，超过就放弃这个目标并记「待重试」，不拖整轮。

试过把发送放子进程做硬超时，但两套 UIA client 会互相踩（单进程 13.3 秒成功、双进程 23.8 秒
报 `COMError`），效果不抵代价，已放弃。现在的 25 秒是协作式超时：单次 OCR 卡住挡不住，
但多轮重试之间能提前收手。

**每次执行都有独立日志**：`broadcast.log`（项目根目录）。任务开始/结束各一行，每个目标一行
（`[2/4] 乙群 → 失败 | 0.0s | 第 1 次尝试 | permanent | 目标已不存在…`），重试各一行。
一眼能看到这一轮成功几个、失败几个、卡在哪个目标。

**失败按性质分开处理**：目标不存在/图片缺失属永久失败，试一次就放弃；锁屏、断屏、`UIA 无响应`、
`COMError` 属临时失败，单目标当场最多试 3 次（间隔 4 秒），仍不行就 5 分钟后只补发没成功的
（已成功的不重发）。一轮总耗时超过 15 分钟就跳过剩余目标，留给下一轮。

**关窗不重发**：任务里记着本轮已成功的目标（`progress`），机器人重启后从断点接着发，
不会把已经收到的人再发一遍。

**发送卡死看门狗**：`send_lock` 被占超过 120 秒（`WECHAT_DEEPSEEK_SEND_HANG_SECONDS`）
就整进程退出（退出码 75），由管理后台或 `一键启动.bat` 重新拉起——答案在发送前已原子
落盘，重启后先核对出站记录再补发，不会重复。正常发送 13~19 秒，有 6 倍余量。

单目标失败不影响同任务其它目标；目标已不存在（群解散、好友删除）在发送前就被拦下（实测 0.02 秒），
不会耗在底层发送重试上。

**关键词广告**：「关键词广告」页配置一组关键词，群里有人聊到（如「便宜的模型」「便宜的 token」）
就自动回一条广告。它不经过 LLM、不写对话记忆，和 @ 回答互不影响。

- **软模式（默认）**：先接话、自曝使用，再插入 `{reply}`（链接/价格），最后降压；
  每条软模板必须含 `{reply}`，只允许 `{reply}` / `{keyword}` / `{sender}`。
  `soft_require_intent=true` 时只回问句或含意图词的消息（「低价api」这种陈述句跳过，
  且不占冷却）。逐群可覆盖成 `hard` 硬广。
- **真 @ 触发者**：广告用 `chat.SendMsg(reply, at=显示名, verify=True)`；成员弹层优先从
  UIA 的 `MentionPopover / chat_mention_list` 选中成员（弹层是独立顶层窗，OCR 读不到时
  按屏幕矩形回退）。点击后不再清空输入框，直接在 @ token 后逐字打字；UIA 输入框把
  `@` token 读成对象替换符 `￼`，成员名以选中的 ListItem 为准，正文读回必须包含；
  OCR 回退则同时要求 `@name` 和正文。重名 / 找不到成员 / 读回不符都跳过，不回退成纯文本 @。
- **拟人节奏**：逐群冷却 `cooldown_seconds ± cooldown_jitter_seconds`（默认 1800±600，
  即 1200–2400 秒），`reply_probability` 默认 1.0，命中后先随机停 1–5 秒再打字；
  账号级写动作仍由 `rhythm.gate('send')` 管。**没有每日/每小时固定条数，也没有发送者冷却。**
- **逐字输入**：正文用 `rhythm.type_text()` 逐字 SendInput（中文 0.12–0.28 秒/字、
  ASCII 0.05–0.14 秒/字，标点后额外停顿；`\n` 用 Shift+Enter，emoji 按 UTF-16
  代理对）。搜索框、文件/图片附件仍用剪贴板。
- **随时改**：关键词、文案、软模板、意图词、模式、冷却/抖动、概率、阅读停顿、逐群开关
  都在 `keyword_ads.json`；机器人按文件变更热加载，保存后下一条消息就生效，不用重启。
- **逐群控制**：每个群可单独启用/停用，也能单独覆盖冷却和模式；未单独配置的群默认**不监听**
  （避免刚上线就把广告铺到全部群），要哪个群就在页面里打开那个群。
- **不自己触发自己**：机器人自己发的消息按 `attr=self` 跳过，再核对一次发送者 wxid，
  并把刚发出去的广告原文当回显忽略（数据库发送者解析失败时的兜底）。
- **可追溯**：每次命中写 `keyword_ads.log`（人看）和 `keyword_ads_hits.jsonl`（后台表格读），
  含群、关键词、时间、模式、@ 对象、打字耗时、发出内容和结果（已发送 / 冷却跳过 /
  非提问跳过 / 概率跳过 / @对象有歧义 / @对象不符 / 发送失败）。

关键词匹配忽略空格和大小写：「便宜的模型」也能命中「便宜的 模型」。这是主动发广告，
建议先在少数群验证文案与命中率再放开；微信对营销内容的频率很敏感。逐字/随机节奏只降低
固定脚本特征，不承诺绕过风控，也不增加额度。

### 使用前提

- 回复需要驱动微信窗口：**桌面解锁、微信可见**（收消息锁屏也能跑）
- 发送只把微信置前，**不会最小化其他程序的窗口**；点击落点被别的窗口压住时跳过本次投递，宁可保留待发也不动你的桌面
- 微信重启后 UIA 控件树会自动热激活，无需手动干预
- 记忆在内存里，重启程序后从零开始

### 微信窗口固定到虚拟显示器（可选）

装上 [IddSampleDriver](https://github.com/ge9/IddSampleDriver) 这类虚拟显示器后，可以把微信窗口
常驻在那块屏上：机器人照常收发消息，物理屏幕上不挡人。

**不需要虚拟屏的用户，把管理后台「配置」页的开关关掉即可**（`WECHAT_DISPLAY_ENABLED`，默认开）。
关掉后机器人不再持续干预窗口位置：发送前不等待目标屏、窗口被拖走不拉回、显示看门狗
也不运行。唯一保留的动作是**微信窗口最小化时还原**——那一步不做就根本发不出消息。
另外，**启动时会做一次恢复**：如果窗口上次被留在了虚拟显示器上（或完全在屏幕外），
机器人把它拉回主屏；已经落在物理屏（含第二块物理屏）上的窗口不动，恢复之后也不再管它。
这个开关只控制机器人是否搬窗口，**不会卸载/禁用虚拟显示器驱动本身**。

开着时按显示器名称匹配（同一页右侧输入框 `WECHAT_DISPLAY`）：

- 启动时校正一次，之后**每次发送前复查**，窗口被拖回主屏会自动拉回
- 匹配靠 `EnumDisplayDevices` 的 `DeviceString` 子串，显示器没装/没启用时只打一行日志，不影响收发
- 挪动窗口用 `SetWindowPos`；窗口最小化时先 `SW_RESTORE`（Windows 忽略对最小化窗口的移动）

**UU 断开后继续运行，须关闭控制端的自动锁屏**：在发起远控的设备上，进入远控窗口
「控制中心 → 安全」，关闭「被控端自动锁屏／远程结束后，被控端自动锁屏」。
手机入口为侧边工具栏「操作 → 安全」。这是 UU 的连接选项，不是机器人配置；若电脑
已经锁屏，关闭选项后还须正常解锁一次，之后再断开。
[UU 官方说明](https://uuyc.163.com/help/20241203/40221_1197695.html)。

2026-11-14 用户确认关闭并断开后，10:46:36—10:49:36 监测中 IddSampleDriver
持续在线、桌面可读；「强」10:48:08 的新来信在 10:48:26 得到自动回复，真实数据库
已查到本人出站消息。Windows 事件记录截至 10:51:47 未出现 10:43:21 解锁之后的
新锁屏或解锁。本轮验证了保持在线与发送，没有模拟显示器掉线后的恢复。

**虚拟屏恢复依赖可交互桌面**：远程控制（UU / GameViewer 等）建连或断连时可能
重建显示拓扑，把虚拟显示器移出桌面。机器人后台看门狗在桌面允许修改拓扑时尝试恢复：

1. 先试 `SetDisplayConfig(SDC_TOPOLOGY_EXTEND | SDC_APPLY)` 把它重新纳入扩展桌面；
2. 还是没出现，说明 PnP 设备本身被禁用了，用 `Enable-PnpDevice` 启用后再扩展一次；
3. 屏回来后立刻把微信窗口搬进去。

实测从「设备被禁用」到「屏恢复 + 窗口归位」约 13 秒。日志前缀是 `[显示]`。

**修复动作必须退避，否则会把整台机器顶卡**。`SetDisplayConfig` 每次都会重建
整个显示拓扑（DWM 重排所有窗口），`Enable-PnpDevice` 还要新起一个 PowerShell
并触发 PnP 重扫设备——这两件事都不便宜。实测锁屏期间曾出现会话不可写，
`SetDisplayConfig` 返回 5（ERROR_ACCESS_DENIED）；需要先恢复可交互桌面，
持续重试不能代替解锁。断开 UU 本身不等于锁屏，所以看门狗按下面的规则跑：

| 情况 | 动作 |
|---|---|
| 屏在 | 每 10 秒只读枚举一次（毫秒级） |
| 屏不在 | 修复一次；失败则间隔翻倍（10 → 20 → … → 300 秒） |
| `rc=5`（会话不可写） | 间隔 60 秒再试，不继续探测 PnP 设备 |
| 连续失败 8 次 | **停止修复动作**，只保留只读检测；屏自己回来立刻归位 |
| 设备探测 | `Get-PnpDevice` 结果缓存 5 分钟，状态 OK 时不重复起 PowerShell |

早期版本是每 10 秒无条件重建一次拓扑，实测在 UU 断开、屏永久救不回来的情况下
几分钟就把机器卡死，所以改成了退避 + 熔断。

**远程断开时还有第二种坏状态：屏没掉，但画面冻结了**。会话变成 disconnected 时
DWM 停止合成，`ImageGrab` 抛 `screen grab failed`，而 `PrintWindow` 抓到的只是
最后一帧静止画面——看起来一切正常，实际搜索框改了、会话列表不重绘，发送会在
死画面上一直找不到目标（实测卡 3~6 分钟，还占着发送锁）。所以发送前多查两道：
会话是不是 `WTSActive`、桌面能不能真的截到东西。任一不过就**暂缓发送并保留答案**，
不暂停机器人。答案先原子写入 `pending_replies.json`；每 10 秒只读检查恢复条件，
桌面与目标屏恢复后自动串行补发，成功后才移出待发。机器人重启也会恢复待发答案，
不会要求对方重发，也不会重新调用模型生成答案。真正的 GUI 发送失败仍暂停机器人，
保留答案供检查窗口后重启续发。日志以 `[待发]` 标记保存、恢复和送达。

临时失败最多补发 **3 轮**（每轮 1+SEND_RETRIES 次）；到上限就删除该条并打
`[!!!]` 记录最后一次失败原因，不会无限循环。补发线程自身连续异常 3 次也会停止，
待发文件保留，重启后再试。

**第三种坏状态：微信停在别的页面，发送在错误页面上找控件**。UIA 交互原来的
假设是「主窗就在对话页」——`guia.send_msg` 里 `already = uia.current_chat() == who`
这一行会直接去读聊天输入框；而 `back_to_chat_tab` 判「要不要点左侧对话按钮」
用的是一个很弱的判据：**会话列表或搜索框在控件树里就算已在聊天页**。

2026-11-14 用户实测指出：微信停在「微信游戏」/朋友圈这类页面时，**左侧会话列表
和搜索框仍然全在树里**，于是这个判据成立、导航栏一次都不点，接着在错误页面上
找聊天输入框。UIA 的跨进程调用没有超时保护，只能在几千个节点里一路遍历
（游戏页的树更大、每个节点都要跨进程查询），于是一次发送走了 **396 秒**；
12:41 那次更久，**45 分钟**没返回——那个线程正是「强」这个会话的 worker，
消息全部排队、补发锁被占，直到重启进程。

修复：**发送前无条件从左侧「微信」栏点起**。`back_to_chat_tab(force=True)`
跳过「看起来已就绪」的误判，每次都点一下导航栏第一颗 tab（「微信」），再判断
当前会话、再输入。日志能看到 `点导航栏「微信」栏第 1 次`。

辅助（降低万一走错页时的遍历量）：

- `_chat_input` 定位结果缓存 30 秒：`current_chat()` 与 `send_text()` 每次发送会
  连着调两次，原来每次全树重搜；
- 结构兜底的遍历预算 4000 → 800；`send_text` 内容没落进输入框时清缓存。

验证（2026-11-14 13:49）：微信停在「微信游戏」页时发一条，日志
`点导航栏「微信」栏第 1 次` → 3 秒后 `聊天页那一片已经渲染` → **16.5 秒**送达，
真实数据库确认出站。修复前同一路径的日志每次都是 `聊天页那一片已经渲染，不点导航栏`。

代价：每次发送多约 1~3 秒（点一次导航栏 + 等页面切回来）。

**会话定位按「微信号 → 备注 → 昵称 → wxid」的顺序搜**。微信搜索框不认 wxid，
只认微信号(alias) / 昵称 / 备注；昵称重名很常见（本账号 20389 个联系人里 `.` 45 人、
`L` 32 人、`ㅤ` 27 人），而微信号在通讯录里唯一。2026-11-14 实测：搜 `God-Cap`
第 1 条就在「联系人」分区，正是「强」（`chenjiaqiang97`）。

- `_resolve_search_keyword` 的候选顺序：alias → remark → nick_name → wxid（兜底）；
- 搜 alias 会把聊过这个号的群一起带出来（实测 4 条里 3 条是群聊），所以结果按
  分区收窄：私聊只认「联系人」、群只认「群聊」；
- 30 秒搜索词缓存：同一会话第二次起只搜成功过的那个词，跳过查库和白搜
  （实测第二次 3.4 秒，候选词只剩 `['God-Cap']`）。

同一轮还修了两个把「明明点开了却判失败」的问题：

- **SetValue 不触发搜索**：搜索框原先用 UIA ValuePattern 写词，值进了框但微信
  没发起搜索，3 个候选词全落空、白耗 32 秒。重试时改用真实粘贴，一次命中 4.1 秒。
- **点开后判定太早**：`_click_ctrl` 后固定等 0.7 秒就读 `current_chat()`，那时
  还读着旧会话名。改成轮询最多 3 秒。

**发送前另有一道探活**（`_uia_responsive`，`UIA_PROBE_TIMEOUT`=2 秒）：独立线程里
新建 Control 对象探测，不响应就返回「UIA 无响应」（命中 `SKIP_SEND_REASONS`：
答案保留待发、不暂停机器人）。它挡的是「整棵树当时就不响应」，挡不住页面错了
还在遍历——上面那条才是主因。单次发送超过 `SEND_ATTEMPT_TIMEOUT`（40 秒）会记
一行「UIA 卡顿，正常 12~14s」；卡住的那次若最终真的发出去了，补发前的出站记录
核对会认出来，不会重复发。

**日志写不进去时必须说出来**：13:24 起 `dafeiyu_bot.log` 整整停了 4 分钟（终端
还有输出、文件没有），排查时被当成「机器人不再收消息」，白绕一圈。现在
`_Tee` 写文件失败会在终端打一行 `[日志] 写入 ... 失败：<原因>`。

两个坑记在这儿：`SetDisplayConfig` 必须声明 `argtypes`（64 位下否则一律返回 87），
并且**不能带 `SDC_SAVE_TO_DATABASE` 或 `SDC_ALLOW_CHANGES`**（带上就变 87，不带返回 0）；
**不要按返回码判断要不要救**——设备被禁用时它也返回 0，只能看屏有没有真的出现。
设备禁用再启用后 GDI 编号会变（实测 97 → 98 → 99 → 101），所以全程不认 `\\.\DISPLAYn`，
只按 `DeviceString` 匹配。

## 库本体（wechatauto）

机器人底层的微信 4.x 自动化能力继承自上游：本地 SQLCipher 解密读取消息/
联系人/朋友圈、UIA+OCR 混合发送、实时监听、媒体下载。命令行工具：

```bash
wechatauto          # 体检 + 交互菜单
wechatauto sessions # 列出会话
wechatauto doctor   # 账号 / 密钥 / 控件树自检
```
