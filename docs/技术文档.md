# wechatauto 技术文档

> 版本：1.0.6 ｜ 适用：微信 4.x Windows 客户端 ｜ 语言：Python 3.9+
> 本文档描述 wechatauto 的设计原理、内部实现与扩展方式，面向二次开发与排障。

---

## 1. 项目概述

wechatauto 是上游 [wxauto](https://wxauto.org) 的复刻版，面向**微信 4.x
Windows 客户端**的自动化库。它**不是网页版**，直接操作本机客户端。

与老版本微信（3.x，暴露 UIAutomation 无障碍树）不同，微信 4.1.12+ 的聊天
区域采用**自绘渲染**（`MMUIRenderSubWindow*`，不同版本后缀不同，如
`MMUIRenderSubWindowHW` / `MMUIRenderSubWindow`），对 UIAutomation / MSAA 完全
不暴露内容。因此本项目拆成两条技术路线：

| 路线 | 模块 | 用途 |
| ---- | ---- | ---- |
| 本地数据库解密 | `wechatauto/db.py` | 读取消息、监听、历史导出、会话/联系人 |
| 坐标 + OCR | `wechatauto/guia.py` | 发送文本/文件/图片、回复、@成员 |

外加两个独立子系统：媒体下载（`media.py`）、朋友圈读取（`moment.py`）。

## 3. 数据库读取子系统（`wechatauto/db.py`）

### 3.1 数据存储布局

微信 4.x 数据位于登录目录下。**不同电脑/账号的目录位置不同**，由
`auto_detect_db_dir()` 自动定位，探测链（`db.py`）：

1. **微信配置文件**：扫描 `%APPDATA%`/`%LOCALAPPDATA%` 下
   `Tencent\xwechat`、`Tencent\WeChat` 等配置目录内的**所有文件**，内容支持
   JSON（`dataDir`/`fileSavePath` 等字段）、纯路径、或任意文本中提取第一个
   Windows 路径（`_extract_path_from_config`）；
2. **注册表**：读 `HKCU\Software\Tencent\xwechat` 等键下含
   path/dir/save 的值（用户自定义保存位置时的补充来源）；
3. **常见默认目录**：`Documents`、用户主目录兜底。

定位结果统一经 `_locate_account_root()` 归一化：兼容
`<root>/xwechat_files/<wxid>_xxxx/db_storage` 与
`<root>/<wxid>_xxxx/db_storage` 两种布局，返回包含 `wxid_*` 账号目录的
父目录（即 `WeChatDB.db_dir`）。仍找不到时可手动传入 `db_dir=` 指定。

典型布局：

```
D:\微信文件\xwechat_files\<wxid>_xxxx\db_storage\
├── contact\contact.db            联系人（昵称、备注、别名）
├── session\session.db            会话列表（未读数、摘要、排序时间戳）
├── message\message_0..4.db       聊天消息（按会话分表 Msg_<md5>，跨库分片）
├── message\media_0.db            语音（VoiceInfo.voice_data，SILK 二进制）
├── message\message_resource.db   文件原名（MessageResourceDetail.packed_info）
├── sns\sns.db                    朋友圈（SnsTimeLine、SnsDataItem XML）
└── ...
```

每个数据库都是 **SQLCipher 4** 加密的 SQLite：页大小 4096、
`PBKDF2-HMAC-SHA512`（加密密钥迭代 256000 次），每页 IV(16) + HMAC(80)。

### 3.2 密钥提取（进程内存只读扫描）

每个数据库有**独立的 32 字节密钥**，运行时保存在微信进程
`com.Tencent.WCDB.Config.Cipher` 配置对象中。`extract_keys()` 流程：

1. 用 `psutil` 枚举 `Weixin.exe` 进程，取可读内存区域；
2. 定位字符串 `com.Tencent.WCDB.Config.Cipher` 的内存地址；
3. 从字符串地址回溯配置对象（`[ptr][len]` 结构），读取数据块；
4. 数据块与固定掩码（`CONFIG_XOR_MASK`）逐字节异或，得到明文配置：
   `x'<64位hex密钥><32位hex盐>'`；
5. 用 SQLCipher 4 的 HMAC 校验规则验证候选密钥（取某库首页试解）；
6. 通过后写入 `%TEMP%\wechatauto_db\<账号>\keys.json` 缓存，
   之后进程内复用（`_cached_db`），无需每次重新扫描。

### 3.3 数据库解密

- SQLCipher 4，`PAGE_SZ=4096`，页尾 `RESERVE_SZ=80` 保留字节
  （IV 16 + HMAC 64）；
- 解密结果按页写入临时工作目录；通过比对源文件 mtime/size 的 stamp
  （`STAMP_VERSION=2`，含缓存格式版本号）判定是否可复用缓存；
- 首次解密 contact.db 约 6s，之后全部秒级；
- 每次打开连接前用 `PRAGMA integrity_check` 兜底，损坏时自动全量重建。

### 3.4 WAL 增量合并（帧盐校验）

微信 `-wal` 是**预分配文件**：checkpoint 时 WAL 头 salt+1 并清零写游标，
但**旧世代帧仍留在文件中**。若合并时不过滤帧盐，会把过期页覆盖进主库，
导致 `database disk image is malformed`。修复方案（`_merge_wal`）：

1. 读取 WAL 头 `salt1/salt2`；
2. 仅合并 **salt 与当前 WAL 头一致**的帧，旧世代帧直接跳过；
3. 合并结果 `PRAGMA integrity_check` 校验，失败自动回退全量重建；
4. 缓存 stamp 版本升级到 2，旧格式缓存强制重建。

### 3.5 消息分片与查询

- 会话名 → `Md5(会话微信号)` → 表名 `Msg_<md5>`；
- 同一会话可能分片在多个 `message_*.db`，查询时按 `sort_seq` 合并排序；
- 关键列：
  - `local_type` → 消息类型（见 `MSG_TYPE_NAMES`）；
  - `real_sender_id`：**该行所在分片** `Name2Id` 的 rowid（不是 `2` 就等于自己，
    也不是全局编号——同一数字在别的分片/别的库里是另一个人，见 issue #34）；
    库层按行所在分片反查成 wxid 放在 `sender_username`；
  - `server_id`：服务端消息 id；
  - `packed_info_data`：图片/视频 md5 等二进制载荷；
  - `sort_seq`：会话内单调递增序号（增量游标用）；
- `get_messages(user, limit, offset)` 倒序取最近消息；
- `get_message_row(user, local_id)` 取含 `packed_info` 的原始行（媒体用）；
- `get_new_messages(user, since_seq)` 返回 `sort_seq > since_seq` 的增量，
  升序排列。

### 3.6 增量消息与水印

`Listener` 每个被监听会话维护一个 `watermark`（最近一次 `sort_seq`）。
轮询时以水印为游标取增量，成功后把水印推进到 `msgs[-1]["sort_seq"]`，
保证不重不漏。回调签名 `callback(msg: dict, listener)`。

### 3.7 会话 / 联系人 / 导出

- `get_sessions(limit)`：读 `session.db` 的 `SessionTable`
  （`username/unread/summary/last_time/last_sender`）；
- `search_contact(keyword)`：对 contact.db 按 昵称/备注/微信号/别名 模糊匹配；
- `get_nickname(user)`：微信号 → 显示昵称（内部维护昵称/发送者索引）；
- `export_history(out, fmt, users, limit_per_chat)`：全量导出
  JSON / SQLite，支持指定会话与条数上限。

## 4. 媒体下载子系统（`wechatauto/media.py`）

### 4.1 媒体存储

| 媒体 | 位置 | 说明 |
| ---- | ---- | ---- |
| 图片 | `msg\attach\<会话md5>\<YYYY-MM>\Img\<md5>.dat` | v2 加密 |
| 语音 | `media_0.db` → `VoiceInfo.voice_data` | SILK 明文 BLOB |
| 文件 | `msg\file\<YYYY-MM>\<原文件名>` | 原名来自 message_resource |
| 视频 | `msg\video\<YYYY-MM>\<id>.mp4` | 仅本地落盘时可用 |

### 4.2 图片 v2 格式

```
[6B 签名 07 08 56 32 08 07] [4B aes_size LE] [4B xor_size LE]
+ AES-ECB 密文段 + 明文段 + 异或段
```

### 4.3 AES 密钥内存反测

图片 AES 密钥是 16 字节 ASCII、账户级稳定，但**仅在微信查看图片时驻留进程
内存**。`detect_image_key()` 的流程：

1. 优先读缓存 `image_keys.json`；
2. 否则对 `Weixin.exe` 内存做定向扫描，对每个候选 16 字节串用 AES-ECB
   解密图片首块，校验 JPEG/PNG 魔数，命中即认为有效；
3. 命中后持久化；也可用 `image_key=` 显式注入。

### 4.4 XOR 密钥推导

异或段密钥是单字节，从同图缩略图 `<md5>_t.dat` 尾部 JPEG 结束标记
`FF D9` 反推：`key = tail[0] ^ 0xFF`。

### 4.5 下载分发

`download_media(user, local_id)` 按 `local_type` 自动分发到
`download_image/_voice/_video/_file`，输出到 `DEFAULT_SAVE_PATH`
（`~/Documents/wechatauto_media`）或自定义 `save_dir`。

## 6. 发送子系统（`wechatauto/guia.py`）

发送走「屏幕坐标 + 本地 OCR」，全部坐标基于**渲染子窗口相对坐标**，
运行时换算为屏幕绝对坐标，保证跨 DPI / 分辨率 / 窗口尺寸一致。

### 6.1 窗口定位与布局

- 主窗口：**多特征兜底定位**（防 Qt 升级改名）。类名前缀
  `Qt51514QWindowIcon` 只是「软条件」之一，`_find_main_window()` 对全部
  可见顶层窗口按「标题含微信 / 类名前缀 / 进程名 `weixin.exe` / 可见 /
  尺寸 ≥ 800px」加权评分，取最高分；完全找不到时退回按标题精确查找。
- 渲染子窗口：类名前缀 `MMUIRenderSubWindow`（自绘内容所在；不同版本
  后缀不同，如 `MMUIRenderSubWindowHW` / `MMUIRenderSubWindow`，
  `_find_render_window()` 按前缀匹配并取面积最大者）；找不到渲染子窗口
  时（Qt 改版等）直接**回退用主窗口矩形计算坐标**，不中断使用。
- `_update_render_rect()` 读 `GetWindowRect` 得到渲染区，`_update_layout()`
  按比例换算各布局常量：
  - `SIDEBAR_RATIO=0.22` → 侧栏宽度 / 渲染区宽度（默认基线）；
  - `SEARCH_BOX_RATIO` → 左侧搜索框；
  - `SEND_BUTTON_RATIO` → 右下角发送按钮检索区；
  - 所有像素坐标均改为比例计算，避免硬编码失效。

### 6.1.1 布局动态校准（防 DPI/布局漂移）

不同机器（DPI 缩放 / 窗口尺寸 / 微信版本）下，固定比例常量可能漂移。
`WeChatGUI` 提供「跑一次永久兼容」的校准机制：

1. **锚点实测**：`calibrate_layout()` 用 OCR 检测「搜索」占位文本
   （文本中心 ≈ 侧栏宽 0.28）反推侧栏宽度；在右下角 OCR 找「发送」
   按钮反推其检索区比例。结果都钳制在合理范围（侧栏比例限
   `[0.14, 0.30]`），**检测失败一律回退默认常量**，宁可不动不误配；
2. **按机器缓存**：结果写入 `~/.wechatauto/layout-<主机名>_<分辨率>.json`
   （含当时的 `render_w/h`）；再次运行时 `_load_layout()` 自动加载，
   与当前窗口尺寸差异 >15% 视为不匹配，自动重新校准；
3. **输入框定位重试**：`get_input_box()` 每轮只取一张完整渲染窗帧，WGC 优先；像素探针在同一帧内扫描，最多尝试两帧。分隔线不可见时保留比例兜底，发送前仍以输入框文本读回校验；缓存矩形绑定渲染 HWND、尺寸、布局档和右侧起点，边界或绑定变化即失效。该路径不再因连续失败自动执行整套布局校准。
4. **显式强制**：`WeChatGUI(calibrate=True)` 强制重新校准；也可在任何
   时候调用 `wx.calibrate_layout()`。

> 说明：微信 4.x 侧栏背景与消息区同为纯白，**像素色差检测不可靠**
> （实测边界两侧均为 255，唯一稳定锚点是搜索框 OCR 文本）。

### 6.1.2 窗口固定到指定显示器（`WECHAT_DISPLAY`）

机器人可以要求微信主窗口常驻某块屏（典型场景：装在 IddSampleDriver 这类
虚拟显示器上，物理屏看不到窗口，但 OCR / 点击照常驱动它）。

- **匹配方式**：`_display_rect(keyword)` 用 `EnumDisplayDevicesW` 遍历活动
  显示器，按 `DeviceString` 子串匹配，再用 `EnumDisplaySettingsW` 读当前
  模式的 `dmPosition` / `dmPelsWidth` 得到该屏在虚拟桌面里的绝对矩形。
  **不依赖 `\\.\DISPLAYn` 编号**——卸载/新增虚拟显示器会让编号重排。
- **校正时机**：`run()` 里 GUI 初始化后一次；`_send_retry()` 每次发送前
  复查。窗口已完整落在目标屏内时**不发任何 SetWindowPos**，避免打断用户。
- **移动细节**：越界才动手；`IsZoomed` 为真先 `SW_RESTORE`（最大化窗口
  `SetWindowPos` 改不动位置）；窗口比该屏大则缩到屏内留边距。
- **失效兜底**：显示器没装/未启用时只打一行日志，不阻断收发；配置为
  空 / `-` / `none` 视为不干预。

> 注意：窗口在虚拟显示器上时，`ImageGrab`（走屏幕 DC 的 BitBlt）有两种
> 失败方式，`_grab_screen` 都要接住：**抛异常**（锁屏）和**静默返回全黑**
> （虚拟显示器不在桌面合成里，BitBlt 调用成功但整块是黑的）。后者更隐蔽——
> OCR 拿到黑图只会返回空列表，看起来像「识别不到」而不是「截图坏了」。
> 两种都回退 `_grab_window` → `PrintWindow(hwnd, hdc, 2)`，已实测在虚拟屏上
> 能拿到完整界面像素。

### 6.1.3 显示看门狗：虚拟屏被远程软件踢掉能自愈

实测环境里装的是 UU 远程 / GameViewer，它们建连或断连时会重建显示拓扑，把
`ROOT\DISPLAY\*` 这类虚拟显示器排出去。表现就是 `_display_rect()` 返回 `None`、
微信窗口被挤到主屏一角甚至最小化成 `(-32000,-32000)`。

`_display_watchdog()` 在后台复查，按下面顺序修：

1. `SetDisplayConfig(0, NULL, 0, NULL, SDC_TOPOLOGY_EXTEND | SDC_APPLY)`；
2. 轮询 4 秒等屏出现；没出现则判定为 PnP 设备被禁用，走
   `_enable_display_device()`（`Get-PnpDevice` + `Enable-PnpDevice`）启用后
   再扩展一次拓扑；
3. 屏回来后 `_ensure_window_on_display(force=True)` 把窗口搬回去。

#### 节奏：必须退避 + 熔断（早期版本把机器卡死过）

`_reenable_display()` 的两步都是重操作：`SetDisplayConfig` 会重建整个
显示拓扑（DWM 重排所有窗口、所有屏重绘），`Enable-PnpDevice` 要新起一个
PowerShell 进程（5.1 启动几百 ms 到几秒、峰值内存上百 MB）并触发 PnP 重扫。

早期实现是「每 10 秒无条件重建一次」，在 UU 断开、屏永久救不回来的场景下
会持续这个循环。实测日志（22:30~22:32）：

```
[显示] IddSampleDriver 不在了（第 7 次检测），尝试重新纳入扩展桌面…
[显示] 扩展拓扑 rc=5
[显示] 扩展拓扑后仍未出现 'IddSampleDriver'，尝试启用显示设备
[显示] 设备状态：ROOT\DISPLAY\0004|OK
[显示] IddSampleDriver 不在了（第 8 次检测）…
```

`rc=5` 是 `ERROR_ACCESS_DENIED`。实测锁屏期间曾因会话不可写被拒，持续重试
不能恢复可交互桌面；但不能把所有 UU 断连都等同于这种状态。当时仍每轮重建一次，
几分钟就把整台机器顶到卡死。断连锁屏设置与实际验收见 6.1.10。

现在的规则（常量在 `dafeiyu_bot.py` 顶部）：

| 常量 | 值 | 含义 |
|---|---|---|
| `WATCH_INTERVAL` | 10s | 屏在时的只读复查间隔 |
| `WATCH_MAX_INTERVAL` | 300s | 退避上限 |
| `WATCH_GIVEUP_AFTER` | 8 | 连续失败多少次后停止修复 |
| `WATCH_DEVICE_CACHE_TTL` | 300s | PnP 设备状态探测缓存 |

分支行为：

- 屏不在 → `_reenable_display()` 返回状态字符串：`'ok'` / `'denied'` / `'failed'`；
- `'denied'`（rc=5）→ **60 秒后再试**，并且**不再起 PowerShell 查设备**
  （权限都没有，启用设备同样会被拒）；
- `'failed'` → 间隔翻倍（10 → 20 → … → 300）；
- 连续失败 8 次 → 熔断，**停止一切修复动作**，只做只读检测；屏一旦自己回来
  （用户重连远程 / 手动启用）下一轮就发现并归位。

用虚拟时钟验证过 600 秒窗口：旧逻辑 60 次重建，新逻辑 8 次（rc=5 场景全在前
105 秒，之后完全静默）。

#### 三个必须记住的调用坑

- **`SetDisplayConfig` 必须声明 `argtypes`**。64 位下不声明，ctypes 把指针按
  32 位整数传，一律返回 87 (`ERROR_INVALID_PARAMETER`)，看起来像参数非法其实
  是调用约定错了。
- **不能带 `SDC_SAVE_TO_DATABASE` 或 `SDC_ALLOW_CHANGES`**。同一拓扑，
  `EXTEND|APPLY` 返回 0，加上任一个就变 87。
- **不能按返回码判断要不要救**。设备被 PnP 禁用时 `SetDisplayConfig` 照样返回
  0，只是拓扑里没有那块屏。判据只能是「屏有没有真的出现在活动桌面里」。

另外设备禁用再启用后 GDI 编号会变（实测 97 → 98 → 99 → 101），所以全程不认
`\\.\DISPLAYn`，只按 `DeviceString` 子串匹配。

实测「设备被禁用」→「屏恢复 + 窗口归位」约 13 秒。

### 6.1.4 窗口校正的两个坑

`_ensure_window_on_display()` 顺序不能反，反过来会静默失效：

1. **先解最小化**。窗口最小化时 `GetWindowRect` 返回 `(-32000, -32000)`，
   而且 Windows 会忽略对最小化窗口的 `SetWindowPos`。不先 `SW_RESTORE`
   就搬不动它。漏这一步的表现是「机器人重启后第一次发送必定截图失败」。
2. **目标屏可能不在**。远程桌面 / 串流软件（GameViewer、向日葵等）接管
   显示输出时会把虚拟显示器挤出活动桌面，`_display_rect()` 返回 `None`。
   这时要退化成「保证窗口留在主屏可见区域」，而不是留在 `-32000`。
   虚拟屏恢复用 `DisplaySwitch.exe /extend` 即可重新纳入扩展桌面。

### 6.1.5 首次布局校准很慢（122 秒）

进程启动后第一次 `get_input_box()` 要初始化 UIA；若当前窗口尺寸与
`~/.wechatauto/layout-*.json` 里的记录差异超过 15%，还会触发完整重校准：
6 次探测各约 12 秒 + 校准约 12 秒，实测 122 秒。之后稳定在 0.1 秒。

这个成本落在发送路径上就是「重启后第一条回复特别慢」，所以
`dafeiyu_bot.run()` 在 `StartListening()` 之后用后台线程跑一次
`_warmup_gui()` 把它挪到启动阶段（只读，不动窗口内容）。

### 6.1.6 发送卡死：UIA 从桌面根遍历（收到但不回）

症状：机器人正常收消息、正常调 LLM、日志里 `[回复]` 也打出来了，但**消息就是发不出去**，
而且日志里连 `[发送]` 失败也没有。多发几条之后彻底不动了。

根因（`py-spy dump` 实测线程栈）：

```
wxmsg-<会话>
  Control.GetChildren        (uiautomation)
  _find_by                   (uia_driver.py)
  WeChatUIA._find_search_list(uia_driver.py)
  WeChatUIA.open_chat
  WeChatGUI.send_msg → Chat.SendMsg → _send_retry
```

`_find_search_list()` 在旧锚点找不到时，有两处**从整个桌面**遍历 UIA 树：

1. `auto.ListControl(searchDepth=0xFFFFFFFF, ...)` 不给 `searchFromControl`
   ⇒ 全局桌面搜索，实测一次 **48 秒**；
2. `_find_by(auto.GetRootControl(), ..., max_depth=25)` ⇒ 桌面下挂着所有
   窗口、任务栏和每个应用，深度 25 能摊出几十万个节点，每个 `GetChildren()`
   都是一次跨进程 COM 调用，**几分钟不返回**。

`SendMsg` 卡在 COM 里不返回 ⇒ 它持有的 `send_lock` 一直不放 ⇒ 后续每条回复
都排在后面堵死。表现就是「收到了但永远不回」。

修复三条：

- 两处遍历的起点都改成 `self._win`（微信主窗口子树），绝不用桌面根；
- `self._win is None` 时直接放弃、交给上层 OCR 回退，**不退回桌面根**；
- `_find_by()` 加 `max_nodes` 节点预算（默认 4000），到量就返回 `None`。

修完 `_find_search_list` 从 48.4 秒降到 3.85 秒（就是它自己的 3 秒 timeout）。

另外补了两条可观测性：`_send_retry()` 成功时也打 `[发送] xxx已发出（第 N 次尝试，X.Xs）`
—— 原来成功不打日志，从日志上完全看不出消息到底发没发出去；发送前先
`_wait_for_display()` 等目标屏回来，避免断屏瞬间进 `SendMsg` 卡死。



进程启动后第一次 `get_input_box()` 要初始化 UIA；若当前窗口尺寸与
`~/.wechatauto/layout-*.json` 里的记录差异超过 15%，还会触发完整重校准：
6 次探测各约 12 秒 + 校准约 12 秒，实测 122 秒。之后稳定在 0.1 秒。

这个成本落在发送路径上就是「重启后第一条回复特别慢」，所以
`dafeiyu_bot.run()` 在 `StartListening()` 之后用后台线程跑一次
`_warmup_gui()` 把它挪到启动阶段（只读，不动窗口内容）。

#### 6.1.14 群发任务：broadcast.py（2026-11-14）

管理后台新增「群发任务」页：多目标、文本/图片、一次性或循环、启停与执行记录。
数据在 `broadcast_tasks.json`，**由机器人进程执行**——后台只读写文件，因为只有机器人
持有微信窗口和 UIA 会话，后台自己去发会和自动回复抢窗口。

**分三层**：

| 层 | 文件 | 职责 |
|---|---|---|
| 模型与调度 | `broadcast.py` | normalize/validate、周期换算、到期扫描、逐目标发送、状态回写 |
| 执行 | `dafeiyu_bot._broadcast_send` | 目标预检、显示器/会话/桌面检查、Chat → SendMsg / SendFiles |
| 管理 | `admin/server.py` + `index.html` | CRUD、目标搜索、列表与表单 |

**时间模型用间隔而不是 cron**：一次性任务记 `run_at`；循环任务记 `unit`（hour/day）+ `interval`，
换算成秒后累加。这样「每天」「每 2 天」「每 7 天」「每 N 小时」是同一个公式，少一套 cron 解析。
`compute_next_run(after_run=True)` 在原来的时间点上加一个周期；落后太多时
`while nxt <= now: nxt += step` 顺延到未来最近一轮——**不连环补发**，否则关机三天回来会一次轰出几十轮。

**调度器**：`BroadcastScheduler(threading.Thread)`，启动后等 8 秒（让微信窗口就绪），之后每 30 秒
`_tick()` 一次。`lock` 传 `None`：`_broadcast_send` 内部自己 `with send_lock`，外层再持一道
非可重入锁会死锁（`_send_retry` 也在这个锁里）。

**两个实测出来的坑**：

1. **`db.get_nickname()` 查不到时把 username 原样返回**，所以「昵称为空 = 目标不存在」这个判断
   永远为假。一个不存在的目标会走完底层发送重试，**实测 169.9 秒**才失败。改用
   `search_contact(tid)` 精确比对 `username`（0.02 秒一次），同一个用例降到 **0.0 秒**。
2. **`WxResponse.message` 可能是 dict**（`{'status','message'}`）。`_resp_text` 只认 str 时会把整个
   dict 打进 `last_detail`，界面上一坨。现在两种都取一句人话。

**文本+图片是两条消息**：微信没有图文合一的类型，`SendMsg` 后紧接 `SendFiles`。结果按
「文本 1 条 + 图片 1 张」记录，不假装合并。

**回写用「读-改-写 + 按 id 合并」**：执行期间用户可能在后台改别的任务，一次性写回会覆盖掉；
`_persist()` 重新读文件、只更新自己那条。

**临时不可用不消耗排期（2026-11-16 补）**：锁屏 / 断屏时 `SendMsg` 返回
`微信窗口不可见（可能锁屏/会话断开）`，这属于「过几分钟就好」，不该把一个
「每 2 天」的任务直接顺延两天——那等于白丢一次。现在 `_broadcast_send` 返回
第三个数 `retryable`；全组都是可重试失败时，调度器只把 `next_run` 推到 5 分钟后、
记 `last_status='retry'`，连续 12 次（约 1 小时）仍不可用才按真失败顺延一个周期。
永久失败（目标已不存在、图片缺失）不走这条路。

#### 群发加固：独立日志、失败分类、断点续跑（2026-11-16）

原来的群发有三个短板：逐目标结果只混在 `dafeiyu_bot.log` 里、临时失败和永久失败
没有统一定义、进程被关窗后重启会把已经成功的目标再发一遍。现在按下面几条改。

**1) 独立日志 `broadcast.log`**（项目根目录，与 `dafeiyu_bot.log` 同级）

任务开始/结束各一行，每个目标一行，重试尝试各一行：

```
[2026-11-16 11:33:12] ===== 任务「测试-每2天循环」开始 id=bt_20261114_231355_c52e 目标=1 待发=1 =====
[2026-11-16 11:33:19] [1/1] 文件传输助手 → 成功 | 7.2s | 第 1 次尝试
[2026-11-16 11:33:19] ===== 任务「测试-每2天循环」结束：成功 1 / 失败 0（共 1 个目标，7.3s）=====
```

失败行带分类：`[2/4] 乙群 → 失败 | 0.0s | 第 1 次尝试 | permanent | 目标已不存在…`；
重试行是 `  ↳ 第 1 次失败（transient），4s 后重试：<原因>`。序号 `[2/4]` 就是「卡在哪个目标」。
`log_line()` 写失败只提示不抛——日志不能把发送拖死。

**2) 失败分类 `classify_failure()`**

`_is_transient` 只认 `SKIP_SEND_REASONS` 那 5 个短语，`COMError (-2147220991, '事件无法调用任何订户')`
不在其中，于是**实测被记成永久失败、`next_run` 直接顺延两天**。现在分三类：

| 类别 | 判据（关键词） | 当场重试 | 下一轮 |
|---|---|---|---|
| `permanent` | 目标不存在 / 图片不存在 / 未找到 | 不试 | 不重试 |
| `transient` | 锁屏、断屏、`UIA 无响应`、`COMError`、`打开会话超过`、超时 | 最多 3 次 | 5 分钟后补发 |
| `unknown` | 没见过的文本 | 最多 3 次 | 5 分钟后补发 |

先判永久再判临时：「目标已不存在」里也有「不存在」，反过来会被临时规则先吃掉。
未知归临时是因为误判成永久的代价更高（一次失败等一整个周期）。

**3) 单目标有限重试**：`_try_target()` 最多试 `TARGET_ATTEMPTS=3` 次，间隔
`TARGET_RETRY_WAIT=4` 秒；永久失败一次就停（不浪费一轮）。最坏单目标约
3×25 秒 + 8 秒 ≈ 83 秒。一轮还有总预算 `TASK_BUDGET_SECONDS=900` 秒，超了就把
剩下的目标记「跳过」——防的是「10 个目标全部掉线」跑掉半小时。

**4) 部分临时失败也补发**：原来只有「**全部**目标都 retry」才进 5 分钟重试，
「3 个里 1 个 COMError」被记成 `partial`、等同终局。现在只要有可重试的失败
就记 `retry`、`next_run=now+300`，`progress` 保留已成功的目标，补发时只发没成功的。

**5) 断点续跑 `progress`**：任务新增字段
`{"run_id": "...", "started_at": 0.0, "done": ["<目标 id>", ...]}`。
每成功一个目标就 `_mark_done()` 落盘；进程被关窗/被杀后重启，`_execute` 看到
`done` 就跳过它——群发是「发出去就收不回」的动作，重发的代价比漏发大。
一轮正常跑完（不管成没成）清空 `progress`，下个周期是全新的一轮。
`normalize_task` 是白名单，`progress` 必须显式列出，否则读一次就被丢掉。

**6) 跨进程锁 `tasks_lock()`**：后台页（`pythonw -m admin`）和机器人（`python -m dafeiyu_bot`）
是两个进程，都写 `broadcast_tasks.json`。原来各自「读-改-写」，后写的那份会把对方刚写的
字段抹掉。现在 `_persist` / `save_broadcast` / `toggle_broadcast` / `run_broadcast_now` /
`delete_broadcast` 全部持一把 `msvcrt` 的 1 字节文件锁（`broadcast_tasks.json.lock`，
最多等 10 秒）。`save_tasks()` 本身仍是 tmp + fsync + `os.replace` 的原子写。

**实测（2026-11-16）**

- 可复现：4 个假目标（成功 / 永久失败 / 两次 COMError 后成功 / 一直 COMError）→
  `broadcast.log` 9 行，`last_results` 与日志逐条一致；永久失败 1 次、临时失败 3 次。
- 部分临时失败 → `last_status=retry`、`retry_count=1`、`progress.done` 保留成功目标。
- 中断续跑：`progress.done=['a']` 时只发 `b`，`a` 零调用。
- 真实群发：重启机器人加载新代码后触发「测试-每2天循环」→ `文件传输助手 → 成功 | 7.2s | 第 1 次尝试`，
  `broadcast.log` 与 `last_results` 一致，`progress` 已清空。
- 单测：`TARGET_ATTEMPTS` 用 mock 降到 1 时全部通过；`pytest` 90 passed。

**会话打开限时（2026-11-16 补）**：一个打不开的目标（搜索没命中、点开的是别的会话）原本在
`find_session` 的多轮放大 OCR + 滚动重试里耗 1~2 分钟。现在群发在 `_broadcast_send` 开头给
`WeChatGUI.open_deadline` 设绝对时间戳（`BROADCAST_OPEN_TIMEOUT=25` 秒），`finally` 里清 0——
值为 0 时行为与以前完全一致，自动回复不受影响。

检查点在**每轮之间**，不是每次调用：`guia._past_deadline()` 被 `open_chat` / `find_session` /
`_scan_vote` / `_chat_open_confirmed` 各层内联检查，`send_msg` 直接调的两处 `uia.open_chat`
也把 `deadline` 传了进去；`uia_driver.open_chat(deadline=...)` 在候选词/重试轮转之间检查。
单次截屏/OCR 或 UIA 跨进程调用本身**中断不了**（丢进子线程 join 会死锁，2026-11-14 实测），
所以这是协作式超时，不是硬超时——真要硬杀只能走子进程隔离。

实测（2026-11-16）：上限临时设 0.01 秒 → `打开 'wxid_…' 已超过时限，放弃` +
`搜索 'wxid_…' 超过时限，放弃` 三条告警，任务进 `retry`（5 分钟后重试、`run_count` 不加）；
恢复 25 秒 → 正常 12.8 秒成功、`next_run` 顺延两天。

**子进程隔离为什么不做（2026-11-16 实测否决）**：为了「单次 UIA 调用卡死也能硬杀」，试过把
发送放到常驻子进程（`Popen` + stdin/stdout JSON 行协议），主进程读超时就 `kill`。结论是
**不可行**：

- 子进程单独跑：`{"ready": true}` → `{"ok": true}`，13.3 秒成功；
- 机器人进程（已持 `WeChatGUI`）再起子进程发同一条：23.8 秒后
  `COMError: (-2147220991, '事件无法调用任何订户')`——`0x80040201` 在 `winerror.h` 里是
  `EVENT_E_ALL_SUBSCRIBERS_FAILED`。

两套 UIA client 操作同一个微信窗口会互相踩，这是进程模型层面的限制，不是代码能绕的。
让主进程在群发期间释放 GUI 再重建能避开，但每个目标要重建 6~10 秒；要让自动回复也走
子进程则要动最敏感的路径。**收益比不成立**：它换的是一个低频场景（历史上只出现过一次
`SendMsg` 卡 396 秒），而现有机制（`UIA_PROBE_TIMEOUT` 探活、`SKIP_SEND_REASONS` 保留待发、
发送后出站记录核对）已经覆盖。

**什么条件下再评估**：`dafeiyu_bot.log` 里 `SEND_ATTEMPT_TIMEOUT`（40 秒）那行达到每周 3 次
以上，说明单次调用卡住是常态而不是偶发；那时再上进程隔离，并且必须配合「所有发送都走
子进程」（主进程完全不初始化 UIA），而不是只在群发路径上用。

### 日志页双来源：机器人日志 / 群发日志（2026-11-16）

管理后台的「实时日志」原来只读 `dafeiyu_bot.log`，群发记录（`broadcast.log`）
只能去文件里翻。现在页面顶部有两个页签，各读各的文件，互不混在一起。

**读取沿用同一套机制**：`tail_log(offset, src)` 里 `src` 选文件（`bot` →
`BOT_LOG`，`broadcast` → `broadcast.BROADCAST_LOG`），路由 `GET /api/logs?src=…&offset=…`
把非法 `src` 回落成 `bot`。所以「按字节 offset 增量续读 + 滚动 reset」这两个
既有行为对群发日志同样成立，切页签看到的是**文件里的历史**（首次读取直接读
文件末尾 64KB），不是「本次打开页面之后才产生的」。

**前端**两个源各存 `offset`/`lines`（`bcLog` 与 `logOffset`/`logLines`），切页签
不会把另一边的续读位置冲掉；切过去立刻拉一次，不等 1.5 秒轮询。群发页签有三态：
没有记录时显示「还没有群发记录…」、首次请求未回时「正在加载…」、请求失败时红字
「群发日志读取失败：…（每 1.5 秒自动重试）」。机器人日志页的筛选 chip
（全部/对话/工具/异常/隐藏库日志）只对机器人日志有意义，切到群发页签时隐藏；
清屏也按当前页签清各自缓冲。

**群发行的着色不能套机器人日志的规则**：`broadcast.log` 的行是
`[时间] ===== 任务「x」结束：成功 1 / 失败 0 =====`，机器人日志那套「含『失败』
就标红」会把成功的执行标成错误。群发用自己的 `bcClass()`：单目标 `→ 失败`、
`第 N 次失败` 算红，汇总行按**失败数 > 0** 才红，`待重试/跳过` 算黄。

**一个顺带修掉的老 bug**：日志文件是 CRLF，行尾的 `\r` 会让
`/^(\[[\d\- :]+\]) ?(.*)$/` 匹配失败——`.` 不吃 `\r`，非 multiline 的 `$`
只认真正末尾，于是整行只能一起打印，时间戳从来没有被单独着色。现在
`r.text.split('\n').map(l => l.replace(/\r$/, ''))` 在两条日志上都去掉了行尾 `\r`
（机器人的 617 行时间戳这才真正拆出来）。

### 群发排期：改成三种互斥周期类型（2026-11-16）

原来的排期把「隔几天」和「每周几」叠在一条链上（`interval` 按步长前进，再用 `weekdays` 筛一遍），
两个条件会互相打架——「每 2 天 + 只选周一」在数学上可能永远撞不上，只能靠 2000 步上限兜底。
现在拆成三种互斥类型，由界面上的 radio 切换：

| 类型 | 字段 | 排期规则 |
|---|---|---|
| 每天发 | `repeat: "daily"` | 按天 +1 |
| 隔几天 | `repeat: "interval"` + `unit` / `interval` | 每隔 N 小时 / N 天 |
| 每月发 | `repeat: "monthly"` + `month_days` | 到选中的日期（1/2/3/6/9 号）触发 |

**互斥**：选中一种只显示对应的输入项；`normalize_task` 把另外两种的字段清空
（`daily` → `interval=1, unit=day, weekdays=[], month_days=[]`；`monthly` → `interval=1, unit=day, weekdays=[]`），
持久化里不留会被排期逻辑读到的残值。

**旧任务兼容**：`repeat` 缺失时由 `repeat_kind(task)` 推断——有 `weekdays` 的走 `legacy_weekday`
（上一版「每周几」逻辑原样保留）；按小时或按天间隔 > 1 走 `interval`；其余走 `daily`。
文件里只有 `unit/interval/anchor` 的老任务读出来不报错、触发规则不变。编辑这类旧任务时，
界面在「隔几天」下显示一行提示「这个任务用的是旧版『每周几』设置（周一/周三）」，保存后按新规则重算。

**每月发的算法**（`_next_monthly`）：

- 时间点沿用原排期时间的时:分（没有就用 anchor），所以「每月 6 号 09:30」能被保留。
- 从当前月往后逐月找：本月里大于「今天」（`after_run`）或「昨天」（保存重算）的选中日期；
  找不到就把月份 +1，最多找 36 个月，不会卡死。
- 落到具体月日后回读 `tm_mon` / `tm_mday` 校验——`mktime` 会把 2 月 30 号悄悄滚成 3 月 1/2 号，
  不校验就会出现「31 号的任务在 3 月 1 日发」。
- 刚发完（`after_run`）不能原地重复，要跳到下一个选中日期。

**保存时重算**：`save_broadcast` 对 `monthly` 和 `legacy_weekday` 都会用新设置重算 `next_run`，
避免编辑后沿用的旧时间落在刚取消掉的那天。

**没有做「每月随机」**：需求第 3 条写的是「可以选择一个或多个日期……到当月的这些日期就触发」，
是固定多日期语义；第 4 条是条件句（如果语义是随机才按随机实现），所以没加随机分支。
真要随机的话，改动点是 `_next_monthly` 在 `days` 里用 `random.choice` 挑一个写进返回值——
但那样每次重算 `next_run` 都会变，排查时反而不好对账。

**实测（2026-11-16 14:52-15:00，真实调用 `compute_next_run`）：**

- 每天 → 11-17 / 11-18 / 11-19 / 11-20
- 每 2 天 → 11-18 / 11-20 / 11-22 / 11-24
- 每 6 小时 → 11-16 ×2、11-17 ×2
- 每月 1/3/6/9 → 12-01 / 12-03 / 12-06 / 12-09 → 01-01 / 01-03（11 月的都过了，正确跨月）
- 每月 31 → 12-31 → 01-31 → **03-31** → 05-31（2 月、4 月没有 31 号，正确跳过）
- 旧「每周几」→ 11-18 / 11-20 / 11-22 / 11-23（和改之前一致）
- 界面：三个 radio 切换时 `#bc-intRow` / `#bc-monthRow` 显隐正确；不选月内日期直接保存被拦下
  「每月发至少要选一个日期（1/2/3/6/9 号）」。
- 落盘：`{"type":"loop","repeat":"monthly","unit":"day","interval":1,"weekdays":[],"month_days":[1,6],...}`，
  `next_run` = **12-01 09:30**（anchor 是 11-17，不在 [1,6]，被 `save_broadcast` 重算到 12-01）。
- 编辑回显：`monthly` 选中、1/6 号勾上、间隔行隐藏、月份行显示、名称和首次时间都对。
- 旧任务四类（只有 weekdays / interval=2 / interval=6 小时 / 只有 type+anchor）都能 normalize + 排期，不报错。

### 函数重名把群发任务页顶掉（2026-11-16）

**现象**：群发任务页一直停在骨架屏（看起来「一直在加载」），但
`curl /api/broadcast` 立刻返回 `{"tasks": []}`，后端没有任何问题。

**根因**：加日志页「群发」标签页时，我给日志渲染函数取名 `renderBroadcast()`。
群发任务页本来就有一个同名函数（渲染任务列表、写 `#bcList`）。JS 的函数声明会
提升，**后声明的覆盖前面的**——日志段那段代码在文件更靠后的位置，于是群发页调用
`renderBroadcast()` 时执行的是「渲染 `#log`」，`#bcList` 里的骨架屏永远没人替换。

**为什么没在自测里发现**：我验的是日志页（两个标签页、空态、错误态全过），
群发任务页当时不在改动范围，没去点它。

**修法**：日志那份改名 `renderBcLog()`（含三处调用点），群发页保持原名不动，
两处都加了注释说明为什么不能叫这个名字。

**验证**（reload 后实测）：`#bcList` 文本是空状态文案「还没有群发任务…」，
`#bcList .skeleton` 数量 0，`bcTasks.length` 0——不再卡加载。

**顺带查清的一件事**：当时任务列表是 0 条，`broadcast_tasks.json` 是
`{"tasks": []}`（mtime 13:29:33）。怀疑是测试污染真实数据，做了实验排除：
往真实文件写一条不启用的任务 → 跑完整 `pytest`（103 passed）→ 文件 sha1 前后
完全一致（`850f50aff215`）、任务还在。会 `save_tasks` 的测试类（
`TestBroadcastTransientRetry` / `TestBroadcastPartialAndResume` /
`TestBroadcastTargetRetry`）都隔离了 `TASKS_FILE`。所以那次空表来自删除操作
（`delete_broadcast` 删到最后一条就会写出 `{"tasks": []}`），不是测试或调度器写的。

**教训**：往一个已有的大 HTML 里加函数，先 `grep` 函数名。这个文件是单文件
应用、没有模块作用域，所有顶级函数共享一个命名空间。

### 发送卡死看门狗（2026-11-16）

子进程方案被否决后剩下的唯一缺口是「单次 `SendMsg` 卡住」——探活（2 秒）只能挡
「整棵树此刻不响应」，挡不住「探活通过、进 `SendMsg` 之后卡住」，卡住期间
`send_lock` 被占死、后面所有回复一起堵。现在用**进程内看门狗 + 外部拉起**覆盖：

- 发送前后写 `_send_started_at`（时间戳，0 = 空闲），不用 `lock.locked()`——
  `Lock` 只知道有没有人占，不知道占了多久。
- `_send_watchdog` 每 5 秒看一次，超过 `SEND_HANG_SECONDS`（默认 120，
  环境变量 `WECHAT_DEEPSEEK_SEND_HANG_SECONDS`）再隔 3 秒二次确认，然后
  `os._exit(75)`。为什么能这么干：UIA 卡住时另一条 Python 线程照常运行
  （实测 `time.sleep` / 纯 Python 忙循环 / ctypes native 阻塞三种情况都能按
  0.5 秒走心跳），而 `uiautomation` 的遍历是「纯 Python 循环 + 每次一个 COM
  调用」，两条路都让出 GIL。
- **120 秒的依据**：`send_lock` 只包 `send()`（两处：`_send_retry` 与
  `_broadcast_send`），锁内正常最长 18.5 秒（图文）；25 秒的「打开会话」上限在
  锁外；`_warmup_gui` 那次 122 秒也不持锁。120 秒是正常值的 6 倍余量。
- **消息不会丢也不会重复**：自动回复走 `_queue_reply`（`fsync` + `os.replace`
  原子落盘）**然后**才 `_flush_pending_replies`；重启后补发前先跑
  `_reply_recorded`，按「同账号 + `seq > after_seq` 水位 + 全文相等」核对，
  已经发出去的直接移出待发。
- **谁来拉起**：`admin/server.py` 的 `_supervise_bot` 只认管理页自己 `Popen`
  的那个进程（不接管 `一键启动.bat` 起的）；`stop_bot` 先置
  `_bot_stop_requested` 再杀，避免「停了又起来」；5 分钟内崩 3 次就停手。
  `一键启动.bat` 那条约 `if "%RC%"=="75"` 后 `goto botloop`。
- **验证开关**：`WECHAT_DEEPSEEK_TEST_HANG_SEND=<秒>` 让 `send()` 先睡这么久，
  模拟卡死；默认 0 = 不启用，生产路径无影响。

实测（2026-11-16）：阈值 3 秒 + 模拟卡住 → 12 秒后打出「发送已卡住 12s（上限 5s）」
且退出码 **75**；强杀机器人 → 7 秒后新进程被拉起（后台日志「机器人退出（code 15），
3 秒后自动重启」）；正常群发 13.1 秒 → 无看门狗日志、进程未重启。

**bat 里的中文只能出现在 `echo` 里（2026-11-16）**：`cmd.exe` 按 ANSI 代码页读
`.bat`，即使第 2 行 `chcp 65001`，**`rem` 行里的中文仍会被拆错**——实测
`rem 这个码必须自动重来；其它退出码多半是用户 Ctrl+C 或真错误，交给 pause。`
被切成两段，后段当成命令执行，报 `'<乱码>用户' is not recognized`。
`echo 中文` 在**块外**没事（那是参数，不当命令解析），所以 `rem`/`::` 一律写
ASCII，中文只放 `echo`。

**但 `if (...)` 块内的 `echo` 中文也会被拆（2026-11-16 补测）**：同一句
`echo 本窗口直接关掉即可。` 放在块外正常，放进
`if "%RC%"=="0" ( ... )` 里就被切成两段、后段当命令执行
（`'=关掉即可。' is not recognized`）。行里没有 `&`/`|`/`<`/`>`/`(`/`)` 任一
ASCII 特殊字符（逐字节核过），所以不是引号或转义问题，是块解析路径的编码差异。
现在的写法：**分支一律 `goto` 到块外的标签**，`echo` 只出现在顶层；
`rem` 全 ASCII。改完用 `cmd /c` 分别跑 RC=0 与 RC=75 两条路径，
`not recognized` 均为 0。

### Ctrl+C 退出与单实例锁（2026-11-16）

用户的现象：Ctrl+C 之后机器人「还在」，再双击 `一键启动.bat` 被
`已有机器人在运行（PID xxx）` 挡住。查下来是两件事叠在一起。

**一、Ctrl+C 到不了进程时，什么都没发生。** `py-spy dump` 抓的是一个「按过
Ctrl+C 但还活着」的实例：主线程 idle 在 `KeepRunning` 的 `time.sleep(1)`
（`wx.py:1660`），listener 线程在 `_find_msg_tables` 里 active，**没有任何
`KeyboardInterrupt` 的痕迹**。信号没送到，跟「卡在收尾」是两回事——先看主线程
停在哪，再判断是信号问题还是清理问题。

**二、信号到了之后，进程也可能赖着不走。** `KeepRunning` 的
`except KeyboardInterrupt` 会 `StopListening` 再 `break`，主线程正常返回；但这之后
要等解释器退出，只要有一个线程卡在 COM/UIA 调用里、或 `atexit` 的清理卡住，
进程就留在后台，下一次启动照样被自己的锁挡住。

**改法：**

- **`_shutdown()`**：`main()` 的 `finally` 里调用。先 `_release_single_instance()`
  主动删锁（`os._exit` 会跳过 `atexit`，锁只能在这里删），再挂一个
  `SHUTDOWN_GRACE_SECONDS=3` 的 daemon `Timer`——3 秒还没退就 `os._exit`。
  正常路径下这个 timer 根本来不及触发（它随进程一起消失），它救的是「主线程
  回来了但进程不退」。
- **先拿锁再初始化**：`_acquire_single_instance()` 移到 `DaFeiYuBot()` 之前。
  初始化要连微信、解密数据库几十秒，放在后面第二个实例会白跑一遍才被拒。
- **残留死锁会被清掉并说明**：锁文件里的 PID 已经不是机器人（进程没了、或 PID
  被系统复用给别的程序）时，打一行
  `[启动] 清掉残留锁（PID 23416 已不在运行）` 再写自己的 PID。判断用
  `_looks_like_bot(cmdline)` 核对命令行（`endswith('dafeiyu_bot.py')`），不只看
  PID 存不存在。
- **`--search` / `--test` 不加锁**：一次性命令不常驻、不抢窗口，加了反而会被
  常驻实例挡住。

**实测（2026-11-16）：**

- `_pid_alive(26376)`（已死）→ `False`；`_pid_alive(999999)` → `False`；
  拿自己 PID 测 → `False`（命令行对不上）。
- 完整走一遍「启动 → 进程终止 → 再启动」：12:02:51 起的那次打印
  `清掉残留锁（PID 26376 已不在运行）` 后正常上线；把它终止（`.bot.pid`
  残留 23416），12:09:03 再起，打印 `清掉残留锁（PID 23416 已不在运行）`，
  12:09:06「大肥鱼已上线」。
- 单测 6 条（`TestSingleInstanceAndShutdown`），证伪两次：删掉 `_shutdown` 里的
  放锁 → `test_shutdown_releases_lock_and_arms_force_exit` 转红；把死锁当活锁
  → `test_stale_pid_file_does_not_block_start` 转红。还原后 `pytest` 96 passed。

**没验到的**：真实按键型 Ctrl+C。`terminal send` 在这台 Windows 上报不出前台
进程，`computer` 不允许对 Mr. Day One 自己的窗口发键，`GenerateConsoleCtrlEvent`
要求同一个控制台、跨控制台会波及发起方。所以「Ctrl+C → 主线程返回」这一段靠
`KeepRunning` 的现有实现 + 单测覆盖，最终要在 `一键启动.bat` 的窗口里按一次确认。

### 一键启动的重启语义（2026-11-16）

用户的要求：「启动前检查是否有服务在运行，有就先结束后再启动，这样就不会每次
启动都报错了」。原来单实例锁让第二次双击变成「提示已有实例 + 退出码 0」，
他要的是**双击等于重启**。

**改法**：新增 `tools/stop_running.py`，`一键启动.bat` 在拉起机器人**之前**跑一次
（放在 `:botloop` 之前，看门狗重启那条 `goto botloop` 不会重复执行它）。它做三件事：

1. 找正在跑的机器人（判据见下）；
2. 停掉：**先调管理后台的 `/api/bot/stop`**；
3. 确认进程真的没了，再删掉 `.bot.pid`。

**为什么必须先调后台 API**：`admin/server.py` 的 `_supervise_bot` 每 3 秒看一次
`_bot_proc`，机器人退出就 3 秒后重新拉起。直接 `terminate` 那个进程，监督线程会
当成「意外退出」把新的拉起来，和用户刚起的实例撞车。`/api/bot/stop` 里先置
`_bot_stop_requested = True`、`_bot_proc = None` 再杀，监督线程就不会再管。

实测证伪：后台持有机器人（PID 1436）时**直接 terminate**，6 秒后变成 PID 11488
（被重新拉起）；走 `/api/bot/stop` 则 8 秒后仍然为空、`bot.running=False`。

**判据：按 basename 认脚本，不看结尾**。原来三处（`tools/stop_running.py`、
`dafeiyu_bot.py` 的 `_looks_like_bot`、`admin/server.py` 的 `find_bots`）都用
`endswith('dafeiyu_bot.py')`。问题在 shell 包装进程：`bash -c "python dafeiyu_bot.py"`
的第三个参数**整条命令是一个字符串**，它以脚本名结尾却不是脚本，被判成机器人后
杀它就是杀用户的终端。改成 `os.path.basename(c) == 'dafeiyu_bot.py'` 后包装进程
的 basename 是整条命令，天然被排除。`--test` / `--search` 这类一次性命令照旧不碰。

**判据和终止序列只有一份，都在 `admin/server.py`**：`is_bot_cmdline(cmd)` 是唯一的
判据（`find_bots`、`dafeiyu_bot._looks_like_bot`、`tools/stop_running.py` 全部转发
到它），`terminate_all(procs, grace)` 是唯一的「先 terminate、宽限期没退再 kill」
（`stop_bot` 与 `stop_running` 共用）。原来这三处各写一份，改 basename 时要同时改
三个地方——重复本身就是口径漂移的来源；管理页的启停判定和清理脚本认的必须是同一批
进程，否则会出现「管理页说没在跑、脚本却认为有」。

**实测（2026-11-16）**：

- 有实例：`[启动] 发现正在运行的机器人（PID 9272），先停掉` → `[启动] 已请求管理
  后台停止机器人` → `[启动] 已结束（PID 9272）` → `[启动] 已清掉旧实例的 PID 锁`。
- 没实例：`[启动] 没有正在运行的机器人，直接启动`，退出码 0。
- `cmd /c` 真跑 bat（probe：机器人换成 `cmd /c exit 0`）：清理段、后台跳过、
  机器人段依次执行，退出码 0，`not recognized` 0 次。
- 单测 4 条（`TestStopRunningCmdline`），其中 `test_shell_wrappers_are_not_targets`
  在修 basename 之前是红的——正是它抓出了误杀 bash 的风险。`pytest` 100 passed。

**没验到的**：双击本身（需要用户在资源管理器里点）。probe 跑的是同一份 bat 的
清理与启动分支，区别只在 `python dafeiyu_bot.py` 换成立即退出。

**第三个坑：`WxResponse` 是 dict 的子类**（`wechatauto/param.py:68`，键是 `status` /
`message` / `data`），`getattr(r, 'message')` 永远是 None。11-14 那次 `_resp_text`
只按属性取，所以「修复」完全没生效，日志里打出来的仍是整个 dict。现在先按 dict 取，
再兼容真正带属性的对象。

**实测（2026-11-14）**：一次性文本 7.0s、文本+图片 18.5s、循环任务 6.9s，三条都在微信数据库里
查到对应出站消息；循环任务执行后 `next_run` 顺延 48 小时（每 2 天）；重启机器人后三条任务
和执行记录完整保留。

#### 6.1.13 虚拟屏开关：WECHAT_DISPLAY_ENABLED

「不用虚拟屏」原先只能靠把 `WECHAT_DISPLAY` 留空或填 `-` 来表达，前端只有一个文本框，
用户不会知道「清空等于关闭」。2026-11-14 加了明确的布尔开关，默认 `True`，保持老行为。

**统一入口**：`_display_target()` 返回当前要固定到的显示器名，空串表示不干预。
四处调用点全部改走它，任何一处漏改都会表现为「开关关了、窗口还在被搬」：

| 位置 | 作用 |
|---|---|
| `run()` 启动校正 | 启动时把窗口放进目标屏 |
| `_wait_for_display()` | 发送前确认目标屏在，不在就主动修一次 |
| `_display_watchdog()` | 每 10 秒复查，屏掉了重新纳入扩展桌面 |
| `_retry_pending_replies()` | 补发前判断目标屏是否就绪 |

**关掉后仍然保留的唯一动作**：`_ensure_window_on_display()` 里的「解最小化」。
窗口最小化时 `GetWindowRect` 返回 `-32000` 哨兵值，且 `SetWindowPos` 对最小化窗口无效，
不先 `SW_RESTORE` 就发不出消息。

**两个踩过的坑**：

1. **`isinstance(True, int)` 为真**，`save_config` 的 int 分支把 `false` 写成了 `0`；
   磁盘上的 `0` 读回来又是 int，再保存还是 `0`，形成死循环。改用显式名单 `_BOOL_KEYS`
   定死语义，`load_config` 和 `save_config` 两端都按它转换。
2. **`GetSystemMetrics(0)` 只有主屏宽度**。开关开着、目标屏又不在时，「窗口在不在可见桌面内」
   用主屏尺寸判断，会把虚拟屏/右侧扩展屏上的窗口（x=1942 > 主屏宽 1920）误判成「在屏幕外」
   然后硬搬回主屏。改用虚拟桌面范围 `SM_XVIRTUALSCREEN`(76) / `SM_CXVIRTUALSCREEN`(78) 等。
   实测日志：修复前 `[窗口] 目标屏不可用，微信拉回主屏 (20,20)`，修复后关掉开关时完全无 `[窗口]` 行。

**验证**（2026-11-14）：关掉开关重启 → 微信停在 `(20,20)` 不动、无搬移日志；打开开关重启
→ `[窗口] 微信移入 IddSampleDriver：(1940,20) 900x650`。

## 6.2 会话定位与点击（防误选与 toggle 关闭）

`open_chat()` 保留现有 HWND/WGC 和点击输入路径，OCR 回退顺序为：

1. 用标题核对当前会话；命中后只额外检查消息区已渲染。
2. `get_sessions()` 先对当前可见侧栏做一次原尺寸 OCR；未命中且未超时时补一次
   放大扫描（本机 900px 宽窗口里原尺寸会把会话名读残缺，实测「龙虾吹水」→
   「花虾吹水」）。`_best_session_row()` 接受完整名、OCR 名是目标的一段、或
   目标名是较长 OCR 名的一段（多出的字符必须是纯符号，否则视为另一个会话）；
   同分候选并列时不猜。活动行经 `_row_is_active(rel_y)` 确认后跳过点击。
3. 未命中或点击后未确认时走 `_search_chat(name)`。**微信 4.x 的搜索结果不在
   主窗画布内，而在同进程的独立顶层窗口里**（实测类名
   `Qt51514QWindowToolSaveBits`，搜索框清空即消失），抓主窗永远看不到候选，
   这是早期版本「搜索总找不到候选」的根因。现在的流程是：
   - **先查通讯录换成微信号**（`_alias_for_name()`，2026-11-20 新增）：微信
     搜索框只认显示名/备注/微信号，不认 wxid；而单字昵称在通讯录里常常重名
     （实测「强」同时对应 `chenjiaqiang97` 与一个陌生 wxid），搜「强」浮层里
     出现两个人，只能靠 OCR 认名字，小字恰好认错。微信号唯一且是 ASCII，
     用它搜索浮层里只剩目标一个。同名对应多个微信号时不猜，退回按名字搜。
   - **入参是 username 时先换显示名**（`_display_name_for()`）：机器人内部
     持有的是 `chat_id`（`chenjiaqiang97`），直接敲进搜索框搜不到任何人——
     2026-11-20 连续四次发送失败就是这个（日志里 `query='chenjiaqiang97'
     alias=None`）。
   - `ensure_visible(activate=True)` 后点搜索框，**逐字键入**搜索词而不是
     剪贴板粘贴——粘贴要求按键那一刻窗口仍持有焦点，两进程争前台时经常落到
     别处，搜索框空着、浮层根本不出现；
   - `_find_search_popup()` 枚举微信进程里可见的 `*ToolSaveBits` 顶层窗口；
   - `_capture_window_frame()` 对该 hwnd 单独 WGC 抓帧，放大 2 倍 OCR；
   - 走名字时 `_popup_result_row()` 只在浮层上半部分（功能 / 聊天记录）取唯一
     最高分候选；走微信号时 `_popup_alias_row()` 认「微信号：xxx」那一行，且
     下界取第一个分区标题（`群聊`/`公众号`/`全部`）——群聊项会写
     「包含：昵称（微信号）」，同样含这个 alias，点进去就发到群里；
     下半部分是「搜索网络结果」，点它只会跳网页，整段排除；
   - 点击坐标 = 浮层窗口矩形 + 浮层帧内 OCR 坐标。
   键入后立刻用 `_typed_into_chat_input()` 检查搜索词有没有落进聊天输入框
   （点击没抢到焦点时就会这样，等于在别人会话的发送区挂一颗雷），发现即放弃。
4. `_chat_open_confirmed()` 最多核对六轮标题；消息区非空不再单独算成功。
   **标题容错一格**：OCR 会把「输」认成「蝓」（实测），不放宽这一格，会话
   已经打开也会被判成没打开、整条发送流程白跑；数字不同则不认（「群1」和
   「群2」不能互相冒充）。

当前 OCR 回退仍调用 `ensure_visible(keep_topmost=True, activate=True)`，坐标点击和键盘输入的前台行为保持原样；本次只是减少定位截图/OCR重试，不代表后台无焦点发送。

**遮挡下的边界（2026-11-20 实测）**：WGC 读取的是窗口表面，与窗口层级无关，
所以画面读取不再受遮挡影响；但真实鼠标点击只能落到 z 序最上层的窗口。只要
有一个不透明窗口盖住微信，点击就到不了微信，必须先 `bring_to_front`。另外
`window_owner_pid()` 会跳过 `WS_EX_TRANSPARENT` 窗口——IDE 的
`Chrome_RenderWidgetHostHWND` 子窗口就是这样盖在微信上方，旧实现据此误判
「落点不属于微信」而放弃投递。

### 6.3 输入框定位与文本输入

- `get_input_box()`：对完整渲染窗调用一次截图（WGC 优先），`_detect_input_box_from_frame()` 在内存中扫描分隔线和输入区边界，不再为每条探针单独截图；最多两帧，失败走比例兜底。几何缓存绑定 HWND/窗口尺寸/布局档/右侧起点，并用当前帧的顶边、底边像素校验后才复用；窗口切换、尺寸变化或边界变化会使缓存失效。发送前输入框文本读回校验保持不变。
  - 判据用**整行白率**而不是沿中心列的像素游走：输入框底色是 250 而非纯白（行白率约 0.85），且框里有文字时中心列会被字头截断，旧写法必然认不出分隔线、每次都走比例兜底。现在是自下而上找白底区间，要求其上方有 1–6 行低白率的分隔线。
  - `_grab_wgc()` 按帧尺寸映射请求矩形：WGC 帧是窗口表面实际像素（实测 886×643），而 `GetWindowRect` 给的 900×650 含边框，旧实现直接拿渲染窗坐标去裁，宽高一越界就返回 None，于是这台机器上 WGC 从未成功、全部回退到桌面截图（遮挡时只能拍到遮挡层）。
- `focus_input()`：点击输入框聚焦；
- `input_text()`：正文改走 **`rhythm.type_text()` 逐字键入**（SendInput
  `KEYEVENTF_UNICODE`），中文 0.12–0.28 秒/字、ASCII 0.05–0.14 秒/字，
  标点后额外停 0.2–0.6 秒；`\n` 用 Shift+Enter，`\t` 换 4 个空格，emoji
  按 UTF-16 代理对发送。打字后 UIA 回读不一致会清空重打一次，仍不一致就
  失败不发，不再回退剪贴板粘贴。
- **搜索框 / 文件、图片附件仍用剪贴板**：搜索词不是发送正文，文件只能走
  `CF_HDROP`，这两类没有逐字等价物。

### 6.4 发送与验证

- `click_send()`：OCR 定位发送按钮（`发送`/`Enter` 图标）点击，
  找不到则直接回车；
- `verify=True` 时用 `WeChatDB` 读回确认：`send_msg` 轮询
  `_verify_sent()`（新消息类型 + 内容匹配），`send_file/send_image` 用
  `_verify_attachment_sent()`（`sort_seq` 基线 + 类型/文件名/`packed_info`
  匹配，图片按类型+时序）。
- DB 实例经 `_get_db()` 缓存复用，避免每次发送验证都重新解析数据库
  （这是历史慢 2.5 分钟问题的根因之一）。

### 6.5 文件 / 图片发送（CF_HDROP）

文件/图片通过 **剪贴板 CF_HDROP + Ctrl+V** 插入草稿再回车发送，绕开自绘
「+ 菜单」定位。`copy_files_to_clipboard(paths)` 写入文件列表剪贴板，
粘贴后 `click_send()`。

### 6.6 回复与艾特

- `reply_msg(text, who, target_text, verify)`：悬停最近一条消息
  （`_last_message_y` 估算）→ OCR 悬停工具栏找「回复」→ 点击 →
  `input_text` → 发送；找不到工具栏回退右键菜单；
- `at_member(member, text, who, verify)`：聚焦输入框 → 清空残留草稿 → 键入 `@` →
  优先从 UIA 的 `MentionPopover / chat_mention_list` 选中成员（弹层是独立顶层窗口，
  OCR 读不到时按屏幕矩形回退）→ **不清空输入框**，直接在 @ token 后逐字键入正文 →
  读回 @ token 和正文才发送；UIA 输入框把 token 读成 `￼`，成员名以选中的 ListItem 为准。
- 读不到 / @ 对象不符 / 正文不符都清空并返回失败，**不回退纯文本 @**；
  `verify=True` 发送后仍走 DB 确认正文送达（@ 对象以发送前的输入框读回为准）。

### 6.6.1 关键词广告：软回复、真 @ 与拟人节奏（2026-11-18）

关键词广告和普通回复是两条路径：

- **普通群回复保持纯文本 `@昵称`**：源码里是 `answer = f'@{at} {answer}'`，
  `_flush_pending_replies()` 调 `chat.SendMsg(entry['answer'])` 没有传 `at`。
  这次只把输入方式改成逐字，不改成真 @。
- **关键词广告走真 @**：`Chat.SendMsg(reply, at=at_name, verify=True)` →
  `guia.at_member()`。先解析 `sender_wxid` 在群成员里的唯一显示名（重名/
  找不到直接跳过）；成员弹层优先按 UIA 的 `MentionPopover / chat_mention_list`
  选中，点击后不调用 `input_text()`（它会 Ctrl+A 清掉 @ token），直接逐字追加正文。
  UIA 输入框的 `ValuePattern` 只给对象替换符 `￼`，成员名以选中的 ListItem 为准；
  正文读回必须包含，OCR 回退则要求 `@name` + 正文同时命中才回车。
- **软模式**：`keyword_ads.json` 的 `mode` 默认 `soft`，逐群可覆盖 `hard`。
  软模板每条必须含 `{reply}`，只允许 `{reply}`/`{keyword}`/`{sender}`；
  `soft_require_intent=true` 时只回问句或含意图词的消息。软跳过不占冷却。
- **节奏**：逐群冷却 `cooldown_seconds ± cooldown_jitter_seconds`（默认
  1800±600 → 1200–2400 秒），`reply_probability` 默认 1.0，命中后
  `pre_delay_min/max` 默认 1–5 秒；账号级写动作仍由 `rhythm.gate('send')` 管。
  **没有每日/每小时固定条数，也没有发送者冷却**。
- **失败不重试**：关键词广告 `_send_retry(..., retries=0)` 只尝试一次，
  避免同一窗口连撞 4 次。

实测与单测见 `tests/test_rhythm_typing.py`、`tests/test_keyword_ads_at.py`、
`tests/test_typing_integration.py` 与 `tests/test_keyword_ads.py`。

真机验证（2026-11-18，🦄Web3+AIGC 交流群）：`Chat.SendMsg('真@读回测试，稍后撤回',
 at='阚强', verify=True)` → 17.8s 返回成功，数据库查到 `@阚强 …`；输入框 UIA 值
只返回 `￼`（对象替换符），成员名来自 `chat_mention_list` 的 ListItem。此前只按
OCR 扫渲染区时，弹层是独立窗口，永远读不到成员名。

### 6.1.7 发送失败被记成「已发出」（except 把 r 置 None）

症状：日志里同时出现两行——

```
[发送] 回答第 1 次异常：RuntimeError: 屏幕截图失败：截图全黑（该区域不在桌面合成里…）
[发送] 回答已发出（第 1 次尝试，5.1s）
```

异常了却说发出去了，群里根本收不到。查库确认：`get_messages()` 里没有这条回复。

根因在 `_send_retry()` 的重试循环：

```python
try:
    with self.send_lock:
        r = send()
except Exception as e:
    last = f'{type(e).__name__}: {e}'
    r = None              # ← 这里
if r is None or not hasattr(r, 'is_success') or r.is_success:
    return True, None     # ← 异常走到这里，被判成功
```

`except` 把 `r` 置 `None`，下一行的 `r is None` 正好命中「成功」分支，于是异常被
吞掉、不重试、报成功。`Chat.SendMsg` 一定返回 `WxResponse`，`r is None` 只可能
来自异常路径。

修复：加一个 `raised` 标记，异常时不算成功，继续走重试（`tests/test_pure.py`
的 `TestSendRetry` 覆盖了这条——把代码改回旧写法，该测试立刻转红）。

### 6.1.8 启动顺序：先校正窗口，再初始化 GUI

`WeChatGUI.__init__` 会按**当时**窗口尺寸做布局校准。如果先 `WeChat()` 再
`_ensure_window_on_display()`，校准就发生在一个断屏遗留的碎片尺寸上
（实测 296×388，portrait 档位），移到 900×650 后又要重校准一次（wide 档位）。
多花十几秒，而且两次校准之间 `origin_x/y` 和 `render_w/h` 短暂不一致，第一次
发送容易截图全黑。

现在 `run()` 的顺序是：

1. `_ensure_window_on_display()` —— 纯 Win32，不依赖 GUI，先把窗口尺寸/位置
   修好；
2. `WeChat()` —— 在正常尺寸上校准一次；
3. 再 `_ensure_window_on_display()` —— `WeChat()` 可能把窗口抢到前台或改回原尺寸。

另外 `guia.ocr()` / `ocr_zoomed()` 入口也补了 `_update_render_rect()`：窗口被
机器人整块搬到虚拟屏上时，缓存里的 origin 会过期，不刷新就会拿旧坐标去截图，
`_grab_window` 的越界守卫返回 `None`，表现同样是「截图全黑」。
`GetWindowRect` 是微秒级调用，相对一次 OCR（100ms+）可以忽略。

### 6.1.9 重复实例检查

`run()` 开头会查一遍「是不是已经有机器人在跑」，有就直接退出。两个实例并存
实测过的后果：同时监听消息导致重复回复、同时驱动微信窗口抢焦点并截图全黑、
各自跑显示看门狗叠加重建拓扑把机器顶卡。

扫描复用 `admin.server.find_bots(exclude_pid=...)`——管理后台的「启动/停止」
判定和这里的检查必须是**同一套谓词**，各写一份会出现「管理页说没在跑、机器人
自己却认为有实例」这种自相矛盾。

两个实现细节：

- **只认 python 进程**。光在 cmdline 里搜 `dafeiyu_bot.py` 会把 bash /
  PowerShell 包装进程也算进来（它们的命令行原样带着整条
  `python dafeiyu_bot.py`），实测一次误报 7 个 PID。
- **`--test` / `--search` 不参与判断**，它们不碰微信窗口。

### 6.1.10 远程断开后画面冻结：暂缓 GUI 发送并保留待发

用户关掉 UU / GameViewer 远程后，实测出现过两种**不同**的坏状态，要分开处理：

| 状态 | 显示拓扑 | `ImageGrab` | `PrintWindow` | 能否发送 |
|---|---|---|---|---|
| 虚拟屏被踢出桌面 | 目标屏不在 | 成功但全黑 | 实时内容 | 先 `_wait_for_display` 等屏回来 |
| 会话断开 / 锁屏 | 屏还在 | **抛 `screen grab failed`** | **冻结的最后一帧** | 不能，整轮跳过 |

第二种最坑：**屏一直在、窗口 rect 也没变**，看起来一切正常，但 DWM 已经停止合成。
`PrintWindow` 抓到的是最后一帧静止画面——搜索框里的字已经改掉（`SetValue` 成功），
列表却不重绘，`find_session` 在死画面上永远找不到目标。

实测日志停在 `[回复]` 之后什么都不打：

```
[08:38:43] [回复] (2.0s) '你好呀，有什么需要我帮忙的？'     ← 然后就没了
```

`py-spy dump` 显示 worker 线程卡在
`WeChatGUI.find_session → open_chat → send_msg → SendMsg`，一直占着 `send_lock`，
后续所有回复全堵。第一次卡了约 3 分钟（08:38:43 → 08:41:57）才以「会话没打开」失败。

截图确认了冻结：搜索框里输着「强」，右侧会话列表还是原样，打开的仍是文件传输助手。

**判据**（两个都要，缺一不可）：

- `_session_active()`：`WTSQuerySessionInformation(WTSConnectState)` 必须是
  `WTSActive`。会话 disconnected 时 UIA 的跨进程调用（`ValuePattern.SetValue`）
  **没有超时保护**，会无限期阻塞。
- `_desktop_readable()`：`ImageGrab.grab()` **抛不抛异常**。虚拟屏上它是
  「成功但全黑」，那种情况 PrintWindow 是实时的、可以发；会话断开时它抛
  `screen grab failed`，说明桌面 DC 不可读、画面已冻结。

**行为**：

- 命中就 `_send_retry` 返回临时失败，不进 `SendMsg`，不置 `paused`；
- `on_message` 生成答案后，先按 Agent、会话 username、来源消息 ID 去重，
  原子写入 `pending_replies.json`，再尝试发送；
- 失败文案命中 `SKIP_SEND_REASONS` 时保留答案，`[待发]` 日志给出原因。
  后台每 10 秒只读检测屏幕、会话和桌面，恢复后调用同一发送入口串行补发，
  不重复调用模型，也不额外重建显示拓扑；
- 临时失败最多补发 `PENDING_MAX_ROUNDS=3` 轮（每轮 1+SEND_RETRIES 次）；到上限
  删除该条并打 `[!!!]` 记录最后一次失败原因，避免外层线程永远重跑同一条。补发
  线程自身连续异常 3 次也会停止并保留 `pending_replies.json`，重启后再试；
- 待发记录绑定原发送账号及会话水位。机器人重启后只处理与当前账号匹配的条目，
  未确认账号或账号不匹配的记录保留不发；先核对同会话水位之后是否已有完全相同
  的本人出站文本，避免发送成功但确认写盘失败后重发。保存与删除都先原子提交
  快照，再替换内存状态。真正 GUI 发送失败仍暂停机器人，答案保留供检查窗口后续发。

旧版本只打印「本轮跳过」，导致已生成的答案永久丢失，重启后的消息监听也不会
重新处理旧来信。2026-11-14 的真实数据库复现：`chenjiaqiang97`（强）08:38:37

**6.1.11 微信停在别的页面导致发送卡住（2026-11-14）**

11:10:54 来信「加这个群」后答案 11:10:57 已保存到待发，但直到 **11:17:33** 才送达，
日志记 `回答已发出（第 1 次尝试，396.3s）`。12:41 又来了一次更久的：强 12:41:36 的
消息触发生成的兜底回复一直没发出去，该会话后续消息全部排队、补发锁被占，直到重启进程。

**根因（2026-11-14 用户指出，事后核对属实）**：不是 UIA 卡死，是**页面判断错了**。

- `guia.send_msg` 的 UIA 分支第一句是 `already = uia.current_chat() == who`，
  它直接去读聊天输入框（`_chat_input`）。
- 而 `uia_driver.back_to_chat_tab` 判「要不要点左侧对话按钮」的规则是：
  **会话列表或搜索框在控件树里就算已在聊天页**（`_chat_page_ready`）。
- 微信停在「微信游戏」/朋友圈这类页面时，**左侧会话列表和搜索框仍然全在树里**——
  于是判据成立、导航栏一次都不点（日志 `聊天页那一片已经渲染，不点导航栏`），
  接着在错误页面上找聊天输入框。
- UIA 的跨进程调用没有超时保护，只能在几千个节点里一路遍历（游戏页树更大、
  每个节点一次 COM 查询），于是单次发送拖到 396 秒 / 45 分钟。

排除法：不是数据库（`get_messages(limit=100)` 0.01–0.04 秒、轮询 30 个会话 0.4 秒）；
不是屏/会话/桌面（`_session_active`、`_desktop_readable`、IddSampleDriver 全正常）；
栈底是 `guia.py:2159`（就是 `already` 那一行）→ `current_chat` → `_chat_input`
→ `Control.Exists` → `WalkControl`，与「在错误页面上找输入框」完全吻合。

修复：

| 文件 | 改动 |
|---|---|
| `wechatauto/uia_driver.py` | `back_to_chat_tab` 新增 `force` 参数；`force=True` 时跳过「看起来已就绪」的判据，**无条件先点一次**左侧「微信」栏 |
| `wechatauto/guia.py` | `send_msg` 的 UIA 分支开头调用 `uia.back_to_chat_tab(force=True)`（独立聊天窗除外），再判断当前会话、再输入 |
| `wechatauto/uia_driver.py` | `_chat_input` 结果缓存 30 秒（`current_chat` 与 `send_text` 每次发送会连着调两次）；结构兜底 `max_nodes` 4000 → 800；`send_text` 内容没落进输入框时清缓存 |

验证（2026-11-14 13:49）：微信停在「微信游戏」页时发一条 →
日志 `点导航栏「微信」栏第 1 次` → 3 秒后 `聊天页那一片已经渲染` →
**16.5 秒**送达、真实数据库确认出站。修复前同一路径的日志每次都是
`聊天页那一片已经渲染，不点导航栏`。代价：每次发送多约 1~3 秒。

保留的辅助措施（与上面配合）：

| 项 | 值 / 行为 |
|---|---|
| `UIA_PROBE_TIMEOUT` | 2 秒；发送前探 UIA 是否响应 |
| `_uia_responsive()` | 独立线程 + 新建 Control 对象探测（对象归探针线程，无跨线程 COM） |
| 不响应时 | 返回「UIA 无响应」，加入 `SKIP_SEND_REASONS` → 保留待发、**不暂停** |
| `SEND_ATTEMPT_TIMEOUT` | 40 秒；只作事后告警（单次发送耗时超了记一行「UIA 卡顿」） |
| 真正 send() | 仍在调用线程里直接执行，不进子线程 |
| 重复发送防护 | 补发前照旧核对同账号、同会话水位之后的完整出站文本 |

**试过但失败的做法**：把 `send()` 放进工作线程 + `join(40)` 做硬超时。真实发送连试
两次都在 40 秒超时，而同一时刻**主线程直发 13.1 秒成功**——`WeChatGUI` 的 UIA 控件
对象在主线程创建，拿到工作线程调用会跨 apartment 阻塞，主线程又卡在 `join()` 里等它
→ 死锁。硬超时这条路在当前架构下走不通。

顺带修了可观测性：13:24 起 `dafeiyu_bot.log` 停写 4 分钟（终端仍有输出），
`_Tee._emit` 的下游异常被 `except: pass` 吞掉。现在写文件失败会在终端打一行
`[日志] 写入 … 失败：<原因>`。这段「日志空白」曾被误读成「机器人停止收消息」。

单测：`test_uia_unresponsive_keeps_answer_pending`（探针 False 时绝不调 send、
原因命中 `SKIP_SEND_REASONS`）与 `test_probe_returns_false_when_uia_call_blocks`

## 7. 消息监听（`Listener`）

```python
from wechatauto import WeChatDB
from wechatauto.db import Listener

db = WeChatDB()
lst = Listener(db, interval=1.0)          # 轮询间隔（秒）
lst.add_listener("filehelper", cb)        # cb(msg: dict, listener)
lst.start()                               # 后台守护线程
lst.stop()                                # 优雅停止
```

- 每个会话独立水印，`watermark` 属性可读写（支持断点续跑）；
- 单次轮询/回调异常不终止监听，写 `sys.stderr` 后继续；
- 数据来源是解密后的本地库，与客户端在线状态无关；
- **回调并发模型（v1.0.2）**：回调在独立工作线程中执行。每个被监听会话
  对应一条**串行**工作线程：同一会话内消息按序处理、不同会话间并行；
  轮询线程只负责读取数据库并分派任务，不会被慢回调（AI 调用 / 图片识别等）
  阻塞。`stop()` 会向工作队列投递停止信号并等待线程退出。

> **跨分片读取（v1.2.1）**：会话消息表 `Msg_<md5>` 横跨多个 `message_*.db`
> 分片。`get_messages` / `get_new_messages` / `_find_media_rows` 现合并全部分片
> 并按 `sort_seq` 全局排序，增量监听 watermark 无重放（续轮 overlap=0 验证）。
> `local_id` 跨分片并非唯一（同一 id 可在不同分片是不同消息类型），媒体下载
> 精确选取由 `local_type` 参数保证（见 7.1）。

### 7.1 防撤回监听（`RecallGuard`）

方案：**增量镜像库 + 媒体备份 + revokemsg 检测与原文恢复**。

```python
from wechatauto import WeChatDB, RecallGuard
from wechatauto.db import Listener

db = WeChatDB()
guard = RecallGuard(db, window=120)     # 回朔窗口（秒）
lst = Listener(db, interval=1.0)
guard.watch(lst, backfill=50)           # users=None: 监听全部会话
lst.start()
```

- `on_msg` 回调：新消息写入 `mirror/recall.db` 的 `mirror` 表；媒体类型
  （图片/语音/视频/文件，`local_type` 3/34/43/49）立即经 `MediaDownloader`
  备份到 `media/`，路径记入 `mirror.media_path`；
- revokemsg 检测：`type == "系统消息"` 且 `content` 含 `revokemsg`；
  `_extract_revoker` 解析 `"昵称" 撤回了一条消息` / `你撤回了一条消息` / 新 XML
  `<content>你撤回了一条消息</content>` 三种格式；新格式（微信 4.1.x 新版弃用
  `time/msg` 字段）的撤回者取 `sender_username` 兜底；
- 原文恢复：`_find_original(chat, revoke_time)` 在镜像 `mirror` 表中按
  `create_time` 位于 `[revoke_time-window, revoke_time)` 且非系统消息、
  `sort_seq` 最近的一条作为原文；终端打印 `[撤回] 撤回者 撤回了一条消息`、
  原文与媒体路径，并 INSERT 进 `recall_events`（`get_recalled()` 查询）；
- 限制：微信撤回后本地通常删原文行，未预回填的历史撤回无原文可恢复；
  同一镜像行的 `local_id` 跨分片冲突时 `INSERT OR REPLACE` 以最近到达为准。

## 8. 消息模型与 UIA 兼容层

- `msgs/`：`BaseMessage` 及子类（`TextMessage/ImageMessage/VideoMessage/
  VoiceMessage/FileMessage/QuoteMessage/LinkMessage/LocationMessage/
  PersonalCardMessage/EmojiMessage/SystemMessage`），`parse_msg()` 统一解析；
- `EmojiMessage`（`type='emotion'`，v1.0.2 新增）："动画表情"消息专属类型，
  `FriendEmojiMessage` / `SelfEmojiMessage` 按收发方向区分。微信 4.x 表情
  content 在数据库中为加密数据，`capture()` 采用「打开会话 → 滚动到底 →
  截取消息区 → 自动裁剪最后一条消息气泡」的屏幕截图方案返回图片路径，
  供上层 AI 视觉识别使用（示例见 `demo_emoji_capture.py`）。

  定位实现（`msgs/mtype.py`）：
  - 微信 4.x 主窗口为 Qt 自绘渲染（`Qt51514QWindowIcon`），不暴露 UIA 子树，
    且 DB 模式消息的 control 是伪控件（`_DBMessageControl.BoundingRectangle`
    恒为 0），无法用控件坐标定位，因此**全部基于屏幕像素分析**；
  - `_pane_capture_img()` 截取消息区全宽画面（渲染顶部到输入框）；
  - 自己发的消息（`attr='self'`）：`_crop_bottom_message()` 用「消息分隔
    空白」定位消息顶部，空白阈值自适应截图高度（约消息区高度的 2.5%），
    跨分辨率/DPI 保持一致；
  - 对方发的消息（`attr='friend'`）：`_crop_by_avatar()` 优先用左侧头像
    圆形彩色块的顶部锚定消息顶部（特征跨分辨率稳定），失败回退
    `_crop_bottom_message()`；
  - 结果再经 `_content_bbox_crop()` 裁掉空白边缘后保存；
  - 会话已打开时跳过 `open_chat`（避免刷新消息列表/切换窗口），并记录
    `[CAP]` 诊断日志与 `~/pane_diag_raw.png` 原图便于跨电脑排查；
- `msgs/mtype.py`：`WxParam.MSG_TYPE_*` 常量到类型类的映射；
- `ui/`：`BaseUISubWnd/Component/Main/NavigationBox/SessionBox/ChatBox`，
  老版 UIA 控件层，微信 4.x 下受限，保留兼容；
- `wx.py`：`WeChat/Chat/Listener` 高层入口，内部按能力分派：
  聊天区读取/监听走 DB，发送走 GUI（`guia.WeChatGUI`）。

## 12. 已知限制

1. **需要微信登录**：数据库密钥存于进程内存，首次需微信运行中（提取后缓存）；
   重新登录密钥变化需重新提取（自动校验失败重扫）；
2. **图片 AES 密钥瞬态**：仅在微信查看图片时驻留内存，命中后持久化
   `image_keys.json`，也可 `image_key=` 显式注入；
3. **发送依赖桌面**：锁屏/会话断开时窗口不响应，发送接口返回明确失败；
   回复/艾特依赖 OCR 工具栏/弹层，弱网或弹层排版变化时可能失败；
4. **视频仅本地可用**：视频 mp4 未落盘时返回 None；
5. **发朋友圈已舍弃**；点赞/评论需热激活 `mmui` UIA 树（`WeChat.Moment`），
   树不可用或锁屏时无法操作；
6. **UI 自动化受限**：4.1.12+ 聊天区自绘，UIA 路线不可用。

## 13. 扩展开发指南

### 新增一个发送类型

1. 在 `guia.py` 仿照 `send_file`/`send_image` 实现原语（定位 → 注入 →
   发送 → 可选验证）；
2. 需要验证时，用 `_target_seq()` 取基线、`_verify_attachment_sent()`
   轮询 DB；
3. 在 `__init__.py` 导出，并加一行式 `quick_*` 封装。

### 新增一种媒体格式

1. 在 `media.py` 参照 `_decrypt_v2` 实现解码原语；
2. 在 `download_media()` 分发处按 `local_type` 接入；
3. 按需在 `_img_md5`/`_find_dat` 补充定位逻辑。

### 新增数据库表

在 `db.py` 的 `_collect_db_files()` 注册新库，用 `_open(rel)` 打开连接，
复用 `_check_merged` 的 WAL 合并与 integrity 兜底。

### 布局常量校准

微信更新导致 OCR 定位失效时，优先检查 `guia.py` 顶部 `*_RATIO` 常量与
`_update_layout()`，而非改硬编码坐标。跨机器/DPI 的布局漂移走自动校准：
删掉 `~/.wechatauto/layout-<机器>.json` 后重启（或
`WeChatGUI(calibrate=True)` / 调用 `calibrate_layout()`）会重新实测并
缓存「搜索/发送」锚点比例。

## 14. 路线图

1. 回复/艾特的跨版本稳定性校准（当前依赖 OCR 工具栏/弹层位置）；
2. 视频消息下载增强（确认 4.x 视频落盘位置）；

4. 支持更多消息类型（小程序、转账、位置等）友好显示（表情消息已在 v1.0.2
   支持）。

**一键启动只弹一个窗口（2026-11-16）**：原来后台用
`start "大肥鱼-后台" cmd /k python -m admin`，双击会多出一个命令行窗口。
现在改成 `start /b "" pythonw -m admin >> admin.log 2>&1`——`pythonw` 没有控制台，
日志进 `admin.log`；`where pythonw` 找不到时才退回 `start /min`。
注意 `start /b` 起的进程与当前控制台同生共死，机器人窗口关了后台也一起结束，
下次双击会重新拉起。
